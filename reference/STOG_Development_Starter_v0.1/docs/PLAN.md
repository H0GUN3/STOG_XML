## 1. 목표와 현재 작업

전체 제품 목표는 협업형 여행 계획과 CELL 기반 개인 기록 지도다. 자체 검색·Instagram·발견·STOBEE는 기존 Place와 여행 바구니에 연결된다.

첫 통합 검증 목표 제안: **실제 인증된 사용자 → 여행 → Instagram 링크 → 캡션/후보/Place 확인 → 선택 장소 바구니 저장 → 중복 없는 결과와 공동 편집 갱신 확인.**

현재 권장 작업: `BOOT-001` 읽기 전용 현황 조사. 아직 저장소를 읽거나 빌드·테스트를 실행하지 않았다.

## 3. 작업 분할과 통과 조건 — 제안

| 묶음 | 현재 상태 | 시작 조건 | 통과 조건 | 범위 제한 |
| --- | --- | --- | --- | --- |
| M0 현황·환경·위험 | PROPOSED | 저장소/환경 접근 확인 | 코드·도구·스크립트 존재, 조건부 연결, 선행 결정을 근거와 함께 기록 | 읽기 전용 조사부터. 라이브 수집·환경 변경은 별도 작업 |
| M1 공통 최소 기반 | PROPOSED | M0 및 현재 기능 계약 승인 | 인증·여행 권한·Place·TripItem을 실제 API/DB로 연결, 버전/재시도/REST+SSE 검수 | 데이터는 현재 검색·후보 대조 표본부터. 전국 전체 수집/전체 SNS 미포함 |

실제 Instagram 서버 두 URL 재검증은 M0/M1 중 별도 승인 작업으로 병행할 수 있다. 출처 JS/JSON/TXT가 없으면 파일 확보 또는 새 구현의 경계를 기록한다. 네트워크·이용 조건 미확인 상태를 우회하지 않는다.

## 4. 당장 생성할 첫 작업

### BOOT-001: 읽기 전용 구현 현황 조사

- 상태: PROPOSED
- 담당자/기한: 미지정
- 근거: v1.4 §1.6, §8, §9.3, §12, §14.12~14.14
- 목적: 기존 구현과 제안만 존재하는 부분을 구분해 불필요한 재작성·확장을 방지한다.
- 포함: 프로젝트 디렉터리, 빌드 설정, 실제 라이브러리/환경 버전, migration, API 계약, 테스트, Instagram 검증 파일 존재 여부 확인.
- 제외: 앱·서버 코드 수정, migration 실행, 라이브 Instagram 수집, 외부 계정 접속/과금 설정 변경, 신규 패키지 설치, 전체 스택 재선정.
- 결과 위치 제안: 이 파일의 현재 상태 표 또는 승인 후 별도 TASK 보고 부분.
- 수용 기준: 실제 확인 경로와 확인하지 못한 이유가 분리되고, 재사용 가능한 구현/정책 미정/환경 장애가 구분되며, 다음 구현 작업 하나의 후보와 필요한 계약을 제시한다.
- 실행 증거: **없음. 이 문서 작성은 BOOT-001 수행이 아니다.**

### 첫 구현 작업을 고르는 기준

이미 존재하는 기능은 검증 후 재사용한다. 없는 기능 중 M1→M2를 가장 짧게 연결하는 것 하나를 선택한다. 예를 들어 현재 코드가 있을 때만 그 경로에 맞춰 `인증된 여행 구성원의 바구니 조회` 또는 `Place를 기존 바구니에 저장`을 검토한다. 실제 파일 확인 전 이러한 예시를 구현 지시나 확정 endpoint로 취급하지 않는다.

## 6. 새 결정 기록 양식

처음부터 ADR 전용 도구나 별도 저장소를 만들지 않는다. 결정은 여기에서 시작하고 독립적인 큰 변경이 생길 때만 분리한다.

```text
결정 ID:
상태: PROPOSED / APPROVED / REJECTED / SUPERSEDED
관련 작업·원문 절:
문제와 현재 막히는 것:
선택한 방법과 더 작은 대안:
범위·DB/API·권한·비용·운영 영향:
검증 방법과 중단/복구 조건:
승인자·승인일·사용자 결정 근거:
구현·검증 증거: 미실행 또는 실제 경로
대체한 이전 결정:
```

빈 승인자와 승인일을 자동으로 채우지 않는다. 제안을 AI 자신이 APPROVED로 승격하지 않는다.
