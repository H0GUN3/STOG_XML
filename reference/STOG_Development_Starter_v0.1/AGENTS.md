## A. 읽기와 우선순위

먼저 README, 이 파일, PLAN의 현재 작업, 관련 원문 절, 작업에 필요한 DB/API/화면 계약을 읽는다. 전체 보고서를 매번 복제해서 별도 요구사항으로 만들지 않는다.

제품 의미는 최신 명시적 사용자 결정과 v1.4 본문을 기준으로 한다. 과거 이력·사용자 제공 검증 보고서·샘플 코드는 현재 정책을 덮어쓰지 않는다. 하위 운영 문서와 TASK가 제품 정책을 바꾸려면 승인자·날짜·근거가 필요하다. 명세와 코드가 다르면 조용히 한쪽을 정답으로 택하지 않고 해당 차이를 보고한다.

## B. 이미 승인된 프로젝트 제약

1. 앱 소스는 Android Java + XML. 주 서버는 Spring Boot Java/Spring MVC, DB는 PostgreSQL이다. 확정 조합을 임의로 재선정하지 않는다.
2. 비용 지출 0원. 과금 조건이 미확인인 실제 외부 연결은 보류한다. 무료 한도 초과를 이유로 유료 모델·API·호스팅·수집 대행·프록시로 전환하지 않는다.
3. Instagram을 외부 링크 기능의 첫 순위로 구현한다. 카카오·네이버 공유는 후속이며 외부 장소 검색 API 후보와 혼동하지 않는다.
4. Instagram 캡션 확보·규칙 파싱은 기본 비LLM이다. STOBEE AI 계획을 근거로 LLM 자동 fallback을 연결하지 않는다.
5. Place, TripItem, 공통 지도/검색/저장, REST+SSE를 재사용한다. Instagram 전용 장소 DB·새 탭·피드·개인 보관함을 만들지 않는다.
6. 단일 주 서버와 단일 DB를 유지한다. Instagram Node.js/Playwright는 제한된 추출 보조 프로세스이며 여행 저장·권한·공용 Place 변경을 담당하지 않는다.
7. 초기 Redis/Kafka/Elasticsearch/벡터 DB/마이크로서비스/Kubernetes 제외. 조건부 대안을 동시에 모두 구축하지 않는다.
8. CELL은 본인 촬영 기록 저장 또는 활성 기록 세션 방문으로만 활성화한다. 링크/검색/바구니 저장·타인 사진 열람으로 CELL·EXP를 만들지 않는다.
9. 바구니와 일정은 같은 TripItem의 상태 이동이다. 승인 없이 복사 정책으로 바꾸지 않는다.
10. 계획 변경은 버전·중복 요청·트랜잭션·커밋 후 SSE 관계를 유지한다. SSE는 원본 데이터가 아니며 재연결 시 조회로 복구한다.
11. 여행 비공개 사진은 작성자와 해당 여행 구성원이 볼 수 있다. 일반 공개 응답·썸네일·파일 권한을 구분한다.
12. 나의 지도 ON/OFF와 줌은 표시 상태다. 기록 세션·CELL 집계를 바꾸지 않는다. 기본 CELL 사진 표현을 별도 높이 연출로 임의 대체하지 않는다.
13. Rain/Snow, Instagram OCR·음성·댓글 수집·원본 재게시·접근 제한 우회는 현재 제외한다.
14. H3 크기/GPS 임계값/큐·시간/P95는 초기 실험값이다. 계정·제공자·성능이 검증됐다고 보고하지 않는다.

## C. 현재 작업 범위 통제 — 새 운영 제안

작업 시작 전에 TASK에 목적, 원문 절, 포함/제외, 선행 결정, 수정 허용 영역, 테스트, 승인 상태를 적는다. 허용된 기능을 구현하면서 필요한 테스트·검증은 포함할 수 있지만, 연관된 다른 제품 기능까지 자동으로 추가하지 않는다.

작업 중 다음 변경이 필요하면 구현 전에 멈추고 승인 요청을 기록한다.

| 승인 필요한 변경 | 기록할 내용 |
| --- | --- |
| 새 제품 동작·출시 범위·후속 기능 앞당김 | 사용자 가치, 원문 대비 차이, 왜 현재 필요한지 |
| 새 의존성·상주 프로세스·DB·외부 공급자 | 기존 구성으로 안 되는 이유, 비용·보안·운영·호환·제거 방법 |
| 권한·공개 범위·삭제/보관 정책 변경 | 영향을 받는 사용자·데이터와 위험 |
| API 파괴적 변경·적용된 DB migration 정정 | 호환성, 이행·복구, 실제 데이터 영향 |
| 운영 환경 쓰기·외부 노출·과금 연결 | 대상 환경, 실행 명령, 승인, 차단/복구 |

이미 승인된 TASK 안의 코드·테스트·합의된 migration 구현에 동일한 승인을 반복해서 요구하지 않는다. 대신 범위가 늘거나 정책이 달라지는 지점에서만 다시 승인받는다.

## D. 구현을 작게 유지하는 규칙 — 새 운영 제안

- 한 AI 실행은 한 작업을 대상으로 한다. 동시에 맡은 작업이 같거나 공통 계약을 수정하면 담당자와 편집 범위를 먼저 조율한다.
- 현재 동작을 구현할 가장 작은 변경을 우선한다. 파일 수·코드 줄 수를 기계적 상한으로 삼아 필요한 검증을 분리하지 않는다.
- 미래의 사용 가능성만으로 공용 프레임워크, GenericService/Repository, 이벤트 버스, 범용 provider engine을 만들지 않는다. 현재 존재하는 외부 IO·트랜잭션·보안 경계는 명확히 분리한다.
- 현재 수용 기준이 사용하는 API·테이블·인덱스만 만든다. 논리 엔티티를 모두 테이블로 변환하지 않는다.
- 성능 변경은 환경·샘플·측정값을 남기고, 조회량/사진량/중복 요청/쿼리/동시성 조정부터 한다. 추가 인프라는 이후의 별도 승인 대상이다.
- 작업과 무관한 코드 스타일 변경·패키지 전체 이동·대규모 리팩터링을 섞지 않는다.
- 선택 기능은 미연결 상태를 명확하게 드러낸다. fixture·사용자 본문 입력·모의 응답을 실제 자동 수집/외부 연동 성공으로 보고하지 않는다.

## E. 생략하지 않을 안전·정합성

계획 버전 검사, 요청 중복 방지, 필요한 DB 트랜잭션, 작업 소유자·여행 구성원·파일 권한, 비공개 사진 필터를 단순화 명목으로 제거하지 않는다.

Instagram URL은 정확한 대상 검증과 하위 요청/네트워크 접근 제한을 포함한다. 개인 쿠키·로그인 세션 복사, CAPTCHA/로그인 우회, 전체 fetch/XHR 원문 상시 수집을 하지 않는다. worker를 공개 인터넷에 직접 노출하거나 사용자 JWT/DB 비밀값을 브라우저에 넘기지 않는다.

조회/작업/재시도/파일 크기/로그·캐시에 상한을 둔다. 아직 정하지 않은 보관기간을 무한으로 기본 설정하지 않는다. 실제 개인정보·토큰·원문 캡션을 일반 로그나 공개 증거 파일에 남기지 않는다.

공유 환경에서 적용한 versioned migration을 덮어쓰지 않는다. 운영 DB 초기화·clean·파괴적 명령·보관 데이터 삭제는 명시적 승인 없이 실행하지 않는다. 복원 불가능한 상태를 정상적인 개발 편의로 취급하지 않는다.

## F. 막힐 때

미정 정책, 코드 부재, 공급자 차단, 버전 불일치, 과금 불확실성을 발견하면 TASK를 BLOCKED로 표시하고 원인과 필요한 결정, 진행 가능한 독립 작업을 적는다. 문서에 없는 기능을 추측해 막힌 부분을 감추지 않는다.

기간 단축, 초대 재사용/재발급, 의도적 중복 장소, 세션 재개·보관, 실제 모델 ID/무료 조건 등은 최신 승인 기록이 없으면 미확정 상태를 유지한다.

## G. 완료 보고

완료 보고에는 반드시 다음 항목을 포함한다.

```text
작업 ID / 기준 문서 절:
변경한 코드·문서·SQL 파일:
실행한 명령과 환경:
통과한 검수 기준과 증거:
실패하거나 실행하지 않은 항목:
기존 동작·권한·데이터·비용 영향:
새 의존성/서비스/API/테이블 변경 유무:
남은 결정 / 다음 작업:
```

실제 파일을 확인하지 않고 존재한다고 보고하거나, 실행하지 않은 테스트·수집·빌드·배포의 성공 로그를 만들지 않는다. `설계 작성`, `코드 작성`, `로컬 테스트 통과`, `외부 환경 검증`, `배포 완료`를 구분한다.

기능 완료는 수용 기준과 실제 증거 검토로 판단한다. 담당자·기한·테스트 환경이 없으면 임의의 이름·날짜·결과를 채우지 않는다.
