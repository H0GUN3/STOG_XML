## 1. 지금 개발을 시작해도 되는가?

**문서 기반 착수는 가능하다. 전체 명세의 일괄 구현이나 외부 배포가 준비되었다는 의미는 아니다.**

v1.4는 제품 기능, 공통 정책, 기술 채택 방향, Instagram 처리 흐름을 정한다. 그러나 다음 경계도 명시한다.

| 원문 위치 | 문서가 실제로 지원하는 결론 | 개발에 미치는 영향 |
| --- | --- | --- |
| §1.4~1.6 | 설계 채택과 코드·배포 완료는 다르다. 이력·보고서보다 최신 본문 정책을 우선한다. | 문서에 나온 기능을 구현 완료로 표시하지 않는다. |
| §8 | 개념 모델과 채택 방향이며 전체 실행 DDL은 아니다. | 현재 기능에 필요한 물리 스키마와 제약을 먼저 정한다. |
| §12 | 기간 단축·초대 재사용·호환성·무료 연결·보관 등 미확정이 남아 있다. | 해당 기능만 보류하고 독립 작업은 진행한다. |
| §14.8 | Instagram REST 경로·필드는 계약 초안이다. | 실제 저장소의 계약과 대조해 요청·응답·오류를 확정한다. |
| §14.12~14.14 | 로컬 두 URL 검증은 사용자 보고다. 참조된 JS·JSON·TXT의 실제 내용은 첨부 확인되지 않았다. | 파일 존재와 재현성을 확인한다. 기존 코드를 재사용했다고 지어내지 않는다. |
| §9.2~9.6 | 비용·외부 조건·성능 수치는 별도 검증 대상이다. | 라이브 호출과 공개 테스트 전에 관련 항목을 확인한다. |

### 바로 할 일

현재 저장소의 코드·빌드·마이그레이션·테스트·실행 환경부터 읽기 전용으로 조사한다. 코드가 이미 존재한다면 재생성하지 않고 차이를 확인한다. 코드가 제공되지 않았다면 그 사실을 기록하고 저장소 접근이 필요한 작업만 보류한다. 기본 문서·테스트 설계는 먼저 진행할 수 있다.

### 먼저 정해야 할 것과 나중에 정해도 되는 것

| 구분 | 예시 | 처리 |
| --- | --- | --- |
| 현재 작업의 선결조건 | 실제 코드 위치, JDK/SDK 조합, 로그인 제공자, API 타입, 필요한 DB 제약 | 해당 구현 전에 확정·검증 |
| 외부 기능 연결 조건 | Instagram 실행환경·이용 조건, Mapbox 비용 차단, 무료 외부 검색 | 미확인 기능만 외부 연결 보류. 가짜 성공으로 대체하지 않음 |
| 해당 기능을 시작할 때의 정책 | 초대 링크 재사용, 의도적 동일 장소 중복, 촬영 위치 부재, 세션 재개·보관 | 해당 작업에 연결한 결정 항목으로 관리 |
| 후속 기능 정책 | 기간 단축, 레벨 곡선, 추천 고도화, 동선 개선 점수 | 전체 착수의 선결조건으로 만들지 않음 |

기존 기능을 임시로 비활성화하거나 출시 범위에서 빼는 것도 범위 변경이다. 필요하면 관리자의 승인을 받고 기록한다. 개발 중 미구현 상태는 완료로 표시하지 않는다.

## 2. 명세 전체와 지금 구현할 범위를 분리한다

프로젝트 규모를 줄이는 첫 방법은 라이브러리를 다시 선정하는 것이 아니라, **지금 검수할 수 있는 기능 묶음 하나를 정하는 것**이다.

아래는 v1.4 §11의 순서를 작게 나눈 작업 제안이며, 기존 제품 범위를 삭제하거나 출시 범위를 확정하는 결정이 아니다.

| 묶음 | 검수 가능한 결과 | 아직 같이 하지 않을 일 |
| --- | --- | --- |
| M0. 현재 상태·위험 확인 | 실제 코드/도구/스크립트 위치, 미실행·장애·외부 조건 목록 | 전체 프로젝트 재생성, 모든 공급자 연동 |
| M1. 공통 여행·장소 최소 연결 | 인증된 사용자와 여행 권한, Place 검색, TripItem 바구니/일정, 버전·재시도·REST/SSE의 최소 사용 흐름 | 전국 모든 데이터 적재, SNS/챗봇/고급 지도 완성 |
| M2. Instagram 첫 연결 | URL → 작업 → 캡션·규칙 후보 → Place 확인 → 사용자 선택 → 기존 바구니 저장 | 카카오·네이버 공유, OCR·음성·LLM 자동 fallback |
| M3. 지도·기록 | 공통 장소 지도, 서버 H3, 촬영 기록, 나의 지도. 이후 같은 흐름에 활성 기록 세션·화면 꺼짐 기록 연결 | 건물 위 사진 연출 고도화, 전국 전체 기록 동시 렌더링 |
| 이후 원문 단계 | 발견·MY → STOBEE → 카카오·네이버 → 측정 기반 고도화 | 승인 없는 삭제·앞당김·기술 교체 |

Instagram은 **외부 링크 지원의 첫 순위**다. 인증·Place·바구니라는 선행 기반까지 없애고 시작한다는 뜻은 아니다. 최소 기반이 준비되는 대로 연결하며, 브라우저 재현성 확인은 M0/M1과 병행할 수 있다. 하나의 작업이 문서 전체를 구현하지 않는다.

## 3. 최소 문서 체계: 상시 관리 MD는 8개부터

역할이 겹치는 별도 PRD, SRS, 아키텍처 백서, 백엔드 설계서 등을 모두 만들지 않는다. 기존 v1.4를 제품 명세로 유지하고 아래 문서는 실행에 필요한 차이만 다룬다.

```text
README.md                         # 이 파일: 시작점, 읽는 순서, 워크플로우
AGENTS.md                         # AI·개발자 작업 가드레일

docs/
  PLAN.md                         # 현재 범위, 작업 상태, 미결정, 결정 이력
  BACKEND.md                      # 전체 구조 + 백엔드 책임·개발 규칙
  DATABASE.md                     # 현재 기능의 DB 계약·제약·마이그레이션 규칙
  API.md                          # 인증·오류·버전·SSE·작업 상태 등 API 공통 규칙
  ANDROID.md                      # 화면 상태·네비게이션·권한·로컬 큐·통신 규칙
  QUALITY_OPERATIONS.md           # 테스트·성능·보안·실행·운영·복구
  tasks/
    _TEMPLATE.md                  # 작업 요청·검수·증거 템플릿
    TASK-xxx.md                   # 승인된 작업마다 필요한 만큼 생성
  reference/
    STOG_Android_App_Project_Specification_v1.4.docx
```

여기에 실제 계약/코드 산출물이 생긴다.

- API 상세: 실제 저장소에 정한 위치의 `openapi.yaml` 한 개를 계약 원본으로 사용한다.
- DB 상세: 실제 Flyway migration SQL을 스키마 변경 원본으로 사용한다.
- 검수 결과: 실행 로그·테스트 리포트·필요한 화면 증거를 작업에서 참조한다.

위 경로는 문서 구조 제안이다. 실제 앱·서버 코드 폴더, 빌드 도구, SQL 경로는 아직 조사하지 않았으며 여기서 확정하지 않는다. 이 묶음에는 README, AGENTS, PLAN, 작업 템플릿만 작성했다. 나머지 5개 상시 문서와 OpenAPI/SQL은 현재 작업이 요구할 때 작성한다.

### 무엇을 기준으로 믿을 것인가?

| 대상 | 기준 원본 | 다른 문서의 역할 |
| --- | --- | --- |
| 제품 의미·권한·사용자 승인 | v1.4 + 승인자/날짜가 있는 후속 결정 | 요구사항을 임의로 다시 정의하지 않음 |
| 현재 구현 범위·진행·보류 | PLAN + 승인된 작업 문서 | 장기 명세를 전부 현재 작업으로 확대하지 않음 |
| HTTP 정확한 필드·상태코드 | 승인된 OpenAPI 계약 | API.md는 공통 규칙·의미·예외를 설명 |
| 실제 DB 형태·변경 | Flyway SQL과 실행 확인 | DATABASE.md는 관계·의미·제약의 이유를 설명 |
| 실제 완료 | 코드·테스트·실행 증거 | 문서의 체크 표시만으로 완료를 증명하지 않음 |

승인된 제품 정책과 API/SQL이 충돌하면 코드나 문서 한쪽을 자동으로 우선하지 않는다. 불일치를 기록하고 해당 변경만 중단해 확인받는다. API/SQL은 요구사항을 바꿀 권한이 아니다.

## 4. 문서를 만드는 순서와 완료 기준

이 순서는 의존관계다. 모든 문서를 길게 완성한 후 코딩하라는 뜻이 아니다. **현재 작업의 부분만 작성 → 구현 → 테스트 → 문서 갱신**을 반복한다.

| 순서 | 문서 | 반드시 들어갈 내용 | 이 단계의 완료 기준 |
| --- | --- | --- | --- |
| 0 | 기존 명세 보존 | 버전·원문·상태·참조 경계 | 기준 버전을 혼동하지 않음 |
| 1 | README + AGENTS | 읽는 순서, 비용/범위/기술 가드레일, 승인·완료 규칙 | 작업자와 AI가 허용 범위를 설명 가능 |
| 2 | PLAN | 현재 묶음, 작업 우선순위·의존성, 제외, 미결정·결정 이력 | 다음 작업 1개의 목적과 검수 기준이 명확 |
| 3 | BACKEND | 단일 Spring/DB/추출기 책임, 트랜잭션, 인증·인가, 외부 IO 경계, 버전 조합 | 현재 작업의 담당 코드와 경계가 정해짐 |
| 4 | DATABASE | 현재 테이블·필드 타입·PK/FK/고유/CHECK, NULL·삭제·날짜 의미, 인덱스 목적, migration | 현재 기능의 유효/무효 상태를 구분하고 빈 테스트 DB에서 적용 가능 |
| 5 | API + OpenAPI | 요청/응답·인증·소유권·오류·버전·재시도·작업 상태·상한 | 앱/서버가 같은 예제를 해석 가능, 성공·실패 계약 존재 |
| 6 | ANDROID | 현재 화면의 로딩/빈값/오류/복귀, 공유 입력·선택 보존·단일 시트, 로컬 큐 | API와 화면 상태가 대응하고 화면 재진입 규칙이 명확 |
| 7 | QUALITY_OPERATIONS | 실행 전부터 테스트 기준, 외부 연결 전에 실행/정지/비밀값/로그/백업·복구 | 현재 기능 테스트 가능, 외부 테스트 시 최소 운영 가능 |
| 반복 | TASK-xxx | 이번 포함/제외·변경 파일·테스트·승인·증거 | 하나의 검수 가능한 변경만 완료 |

DB와 API는 4→5로 초안을 잡되 함께 검토한다. 전체 DB부터 만들거나 전체 API부터 확정하지 않는다. QUALITY_OPERATIONS의 테스트 항목은 코드 전에 작성하고, 운영 절차는 첫 외부 테스트 전에 채운다. 작업 템플릿은 2단계부터 사용한다.

## 5. 백엔드·DB·API 문서에 적을 STOG 규칙

### BACKEND.md

v1.4 §5, §9, §14.3을 참조해 다음만 구체화한다.

- 주 서버는 Spring Boot/Spring MVC 한 개, DB는 PostgreSQL 한 개. Node.js/Playwright는 Instagram 추출 보조이며 공용 DB 수정·여행 권한·저장을 맡지 않는다.
- 업무 모듈을 코드 안에서 구분한다. 현재 기능이 쓰지 않는 서비스·인터페이스·범용 플러그인 구조는 만들지 않는다.
- 일반 여행 API의 DB 트랜잭션 안에서 브라우저·외부 API·AI·대용량 미디어를 기다리지 않는다.
- 계획 변경은 권한, 동일 요청 재시도, plan_version, 데이터 변경, 요청 결과, 커밋 후 SSE의 관계를 명시한다. 같은 버전을 두 방식으로 증가시키지 않는다.
- 소유자·여행 구성원 권한을 각 리소스에 적용한다. 로그인 성공과 모든 리소스 접근 허용은 구분한다.
- worker 통신 방식, 실행 주체, 시작/종료·타임아웃은 저장소와 실행환경을 확인한 후 결정한다. HTTP/프로세스 호출 등을 모두 동시에 구현하지 않는다.

### DATABASE.md

v1.4 §8의 모든 논리 엔티티를 즉시 물리 테이블로 만들지 않는다. 첫 흐름에서는 User·Trip·TripMember·Place·TripItem과 인증/중복요청에 필요한 구조를 구체화하고, Instagram 때 ImportJob을 추가한다. 기존 코드에 존재하면 먼저 재사용 가능성을 확인한다.

필수 규칙은 TripItem 바구니/일정 상태의 무효 조합 방지, 여행과 항목의 소속, request_id의 고유 범위와 입력 해시, 계획 버전의 원자적 변경이다. 날짜·순서 필드의 실제 타입, NULL 조합, FK 삭제 동작은 계약 검토로 확정한다. 의도적 같은 장소 반복은 원문 미확정이므로 임의의 영구 고유 제약으로 정책을 결정하지 않는다.

CELL 단계에서 `(user_id, cell_id)` 최초 활성화 고유성을 다룬다. ImportCandidate/PlaceExternalRef 등 논리 구분은 조회 요구와 제공자 조건을 보고 기존 매핑·제한 JSONB 등으로 표현한다.

공유 환경에 적용한 versioned migration을 수정·삭제하지 않고 새 migration으로 정정한다. 이는 Flyway 공식 권장과 맞는다.[S2] 운영 DB 초기화·`clean`·무검토 `DROP`은 금지하고, 스키마 자동 변경을 Flyway와 중복으로 운영하지 않는다. 신규 인덱스에는 대응 쿼리와 검증 이유가 있어야 한다.

### API.md와 OpenAPI

`API.md`는 권한, 오류 응답 의미, 날짜·좌표·ID 표현, 페이지/개수 제한, plan_version/request_id, SSE와 작업 상태의 의미를 설명한다. 정확한 endpoint·필드·타입·성공/오류 예제는 OpenAPI에 한 번 작성한다. OpenAPI는 HTTP 인터페이스를 기술하는 형식이며 또 하나의 서버를 도입하는 것이 아니다.[S1]

v1.4 §14.8의 Instagram 경로는 초안으로 입력한다. API가 정해지지 않은 부분을 기존 구현처럼 적지 않는다. 작업 COMPLETED, 후보 MATCHED, 사용자 저장 성공을 구분한다. 202 접수 지연과 전체 추출 완료 지연도 별도로 다룬다.

### ANDROID.md

공유 입력 복원, 중복 접수 방지, 작업 ID/선택 상태 보존, 화면 이탈 시 조회 중지, 검색→지도→검색 복귀를 현재 화면 단위로 작성한다. Instagram 링크만으로 CELL·EXP·Post가 생기지 않는 것을 검수한다. 위치 서비스·Room·WorkManager·지도 렌더링 역할 분리는 실제 기록 단계에서 구체화한다.

## 6. 작업 한 개의 표준 흐름

```text
기준 확인
→ 현재 코드 읽기
→ 작업 1개 선택
→ 미결정·영향 범위 확인
→ 필요한 DB/API/UI 계약과 테스트 작성
→ 승인된 범위만 구현
→ 빌드·테스트·실행
→ 변경 diff·의존성·보안·비용 검토
→ 문서·증거 갱신
→ 완료 승인
```

작업 크기는 파일 수가 아니라 **독립적으로 검수 가능한 변경 하나**를 기준으로 잡는다. 관련 테스트를 같은 변경에 포함한다. 리뷰 가능한 작은 변경을 권장하는 Google의 개발 검토 지침도 같은 방향이다.[S3]

여러 AI가 작업하더라도 같은 migration/API/공통 설정을 동시에 고치지 않도록 작업별 편집 책임자를 정한다. 한 AI 실행에는 한 작업을 주고, 새 기능 필요성이 보이면 PLAN의 제안으로만 기록한다. 문서 길이보다 현재 작업 범위가 중요하다.

### 상태

`PROPOSED → READY → IN_PROGRESS → REVIEW → DONE`

- PROPOSED: 범위·정책이 검토 중이다.
- READY: 의존성, 포함/제외, 필요한 계약, 수용 기준이 정해졌다.
- IN_PROGRESS: 승인된 작업을 수행 중이다.
- REVIEW: 코드·증거·문서 검토가 남았다.
- DONE: 수용 기준에 대한 실제 증거와 검토가 있다.
- BLOCKED: 이유·필요한 결정·막힌 작업만 명시한다. 나머지 독립 작업을 막지 않는다.

승인 정책 상태, 작업 진행 상태, 실행 증거 상태를 하나로 합치지 않는다. 새 문서가 생겼다는 이유로 기능 작업을 DONE으로 바꾸지 않는다.

## 7. 과도한 확장을 막는 가드레일

세부 규칙은 [AGENTS.md](AGENTS.md)를 따른다. 다음은 제안 운영 규칙이다.

| 제한할 것 | 실제 통제 방식 |
| --- | --- |
| 요청하지 않은 화면·자동화·추천 기능 | 모든 작업에 원문 절과 현재 요구 ID를 붙인다. 연결 없는 코드는 승인 전 추가하지 않음 |
| 새 DB/브로커/검색엔진/서비스 | 기존 구성으로 해결하지 못한 측정 자료와 운영 책임, 비용 검토, 승인 기록을 먼저 요구 |
| 전체 미래 스키마·API 생성 | 현재 수용 기준이 사용하는 테이블·계약만 작성 |
| 범용 프레임워크·중복 추상화 | 현재 구체적 호출·테스트가 없는 계층은 만들지 않음. 외부 IO·보안 경계처럼 현재 필요한 분리는 허용 |
| 무제한 데이터·작업 | 조회/사진/업로드/큐/재시도/외부 호출에 상한을 두고 실제 값은 측정·승인 |
| 문서만으로 과금 0원 주장 | 실제 계정·이용 조건 확인 전 연결 보류. 무료 한도 초과 시 유료 fallback 없음 |
| 테스트를 안 하고 완료 선언 | 실행 명령·환경·결과·실패/미실행·증거를 필수 기록 |
| 작업과 무관한 대규모 리팩터링 | PLAN에 별도 제안으로 분리 |

v1.4가 초기 제외한 Redis, Kafka, Elasticsearch, 벡터 DB, 마이크로서비스, Kubernetes를 재도입하지 않는다. GraphHopper 같은 조건부 대안도 필요성이 확인되기 전에 TMAP과 병렬 구축하지 않는다.

**단순화해도 삭제하면 안 되는 것:** 권한 검사, 중요한 데이터의 트랜잭션·재시도/동시성 일관성, 비공개 파일 인가, 외부 URL/브라우저 접근 제한, 시간·용량 상한, 데이터 복구 가능성. SSRF 방어는 URL 문자열만 보는 문제가 아니며 네트워크 제약 등을 포함하는 보안 설계 대상이다.[S4]

MD는 행동 지침이지 실행 권한 경계 자체는 아니다. 실제로는 필요한 작업에만 파일·명령·외부 자격증명을 허용하고, dependency/build/SQL diff와 테스트를 검토한다. 자동 검사는 로컬에서 시작할 수 있으며 유료 CI나 별도 운영 플랫폼을 전제하지 않는다.

## 8. 최소 운영 문서와 증거

QUALITY_OPERATIONS.md는 다음 항목을 한 파일에서 시작한다.

| 영역 | 최소 기록 |
| --- | --- |
| 실행환경 | 실제 버전, 실행 위치, 포트·주소, 비밀값 이름, 프로세스 책임자 |
| 시작/정지 | DB·주 서버·추출기 시작 순서와 실제 확인된 명령, health 점검 |
| 외부 접속 | 공개되는 API, TLS, 접근권한, worker/DB 비공개, 소셜 callback |
| 제한 | worker/대기열/타임아웃/재시도/파일·로그 용량, 외부 API 한도 |
| 장애 | 추출기 중단/작업 임대 만료, DB/디스크 문제, SSE 재연결, 외부 한도 제한 |
| 개인정보 | JWT/쿠키/개인 GPS·사진/캡션 원문을 일반 로그에 남기지 않는 규칙 |
| 백업·복구 | DB와 미디어의 대상·주기·보관/권한, 테스트 복원. 미확정 수치는 표시 |
| 배포 | 검증된 빌드·설정·migration, smoke test, 중지/복구 계획 |
| 성능 | 일반 API와 202 접수·추출 완료·사용자 확인·지도 시간을 분리 측정 |

실제 서버를 확인하기 전 실행 명령과 경로를 성공 사례처럼 채우지 않는다. 복구 정책은 `배포 파일을 되돌리면 DB도 복구된다`고 가정하지 않는다. 실제 데이터 삭제·공개 전에는 관련 정책과 검증을 마쳐야 한다.

## 9. 지금 AI에게 줄 첫 작업

첫 작업은 전체 구현이 아니라 **기존 구현 현황과 개발 시작 조건 점검**이다.

```text
README.md, AGENTS.md, docs/PLAN.md를 읽고 v1.4 §1.6, §8, §9, §11~14를 확인해라.
이번 작업은 BOOT-001: 읽기 전용 구현 현황 조사다.
코드/빌드/DB migration/API/테스트/추출 스크립트가 실제로 존재하는지 확인해라.
기존 기능을 재생성하지 말고, 확인된 파일 경로와 미확정만 보고해라.
외부 유료 호출, 운영 DB 쓰기, 신규 의존성 설치, 앱/서버 코드 수정은 하지 마라.
기존 실행 명령의 존재·필요 환경을 조사하되 이번 단계에서 외부 접근/쓰기 명령은 실행하지 마라.
끝에 M1의 첫 구현 작업 1개, 관련 계약, 선행 결정, 검수 기준을 제안해라.
저장소 접근이 없으면 존재하지 않는 코드·로그·스크립트를 추정하지 마라.
```

현재 저장소 접근을 제공받기 전에는 BOOT-001도 실행 완료로 표시하지 않는다. 역할·기한·서버 사양이 제공되지 않았으므로 여기서는 인력별 일정이나 완료 날짜를 확정하지 않는다.
