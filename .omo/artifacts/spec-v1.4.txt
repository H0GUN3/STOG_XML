1. 문서 개요
본 문서는 STOG Android 앱의 제품 개념, 정보 구조, 화면별 기능 요구사항, 협업 규칙, 지도·카메라·SNS·AI 기능, 데이터 수집 전략 및 기술 스택을 개발 관점에서 일관되게 정의한다.
1.1 프로젝트 목적
여행 계획을 혼자 작성하는 도구가 아니라 여러 사용자가 하나의 여행을 함께 편집하고 관리할 수 있는 협업형 여행 플래너를 제공한다.
사용자가 STOG 카메라로 남긴 사진 기록과 직접 시작한 여행 기록 세션의 방문 흔적을 지도 위 육각형 CELL에 축적하여 “나만의 지도를 채워 나간다”는 경험을 제공한다.
여행 계획, 여행 중 장소 탐색, 사진 기록, 여행 후 회고와 공개 공유까지 하나의 앱 안에서 연결한다.
1.2 핵심 제품 가치
가치
설명
협업
여행 구성원이 동일한 여행의 정보, 바구니, 일정을 함께 수정하고 공유한다.
기록
STOG 카메라 기록 또는 사용자가 시작한 여행 기록 세션의 방문을 CELL에 연결해 실제 활동 흔적을 지도에 남긴다.
발견
관광정보와 다른 사용자의 공개 기록을 통해 주변 장소와 여행 아이디어를 발견한다.
연결
Instagram 등 외부 공유 링크에서 장소를 가져와 기존 여행 바구니로 연결하고 일정 작성 과정을 단축한다.
개인화
STOBEE가 현재 위치와 대화 맥락을 바탕으로 주변 장소 탐색을 보조하고 여행 바구니로 연결한다.
1.3 범위 구분
초기 구현 범위Android 앱, 자체 장소 검색, 여행 생성/협업, 여행 바구니·일정, 지도/동선, CameraX와 CELL 기록, 발견·MY·STOBEE를 유지한다. 외부 링크 유입은 Instagram을 먼저 구현하며, 최소 인증·Place·TripItem 연결 이후 조기에 검증한다.
후속 구현 범위카카오·네이버 지도 공유 링크는 Instagram 이후 구현한다. 고도화된 추천·동선 개선, 레벨 세부 밸런싱과 세부 알림 정책은 단계적으로 완성한다. Instagram의 우선순위 승격은 서비스 구현·배포 완료를 뜻하지 않는다.
1.4 승인 범위와 비용 원칙
현재 프로젝트는 추가 비용 지출 0원을 전제로 한다. 무료 한도 내 이용과 과금 가능 서비스는 구분하며, 한도를 넘겨 유료로 전환하거나 유료 대체 서비스를 자동 호출하지 않는다. 계정·모델·지도 제공자의 실제 조건을 확인한 뒤 연결한다.
이번 개정은 최신 사용자 결정과 권장 설계를 문서에 채택한 것이다. 앱·서버 구현, 성능 측정, 외부 서비스 허용 여부나 과금 설정의 검증 완료를 뜻하지 않는다. Instagram 로컬 검증은 사용자 보고서에 근거하며, 여행 기간 단축 정책 등 기존 미확정은 유지한다.

1.6 AI 구현 도구용 해석·상태 규칙
이 문서는 사람이 읽는 기획 설명과 AI가 구현할 때 필요한 계약·예외·근거를 함께 담는다. 길이를 줄이기 위해 검증 한계나 권한·실패 처리를 생략하지 않는다. 문서의 채택 상태를 구현 완료 상태로 바꾸어 해석하지 않는다.
상태
해석
확정 / 채택 설계

보고된 검증
사용자가 제공한 로컬 검증 보고서의 관찰값. 이번 편집에서 스크립트·JSON을 재실행하거나 대조한 결과가 아니다.
초기 실험값 / 조건부

임의로 기능이나 정책을 추가하지 않는다. 후속은 제외·삭제가 아니라 구현 순서의 뒤쪽이다.

2. 핵심 용어 정의
용어
정의
STOG
STEP + LOG. 발걸음과 기록을 하나의 지도 경험으로 연결하는 서비스 이름.
CELL
지도 위 육각형 단위. STOG 카메라 기록 저장 또는 사용자가 활성화한 여행 기록 세션에서 방문이 확인될 때 활성화된다. 갤러리 등록·장소 검색·저장만으로는 활성화하지 않는다.
여행 바구니
STOG 자체 검색, 외부 공유 링크, STOBEE 추천, 발견 게시물 저장 등을 통해 “여행 일정에 넣기 전” 임시 보관하는 장소 목록.
여행 일정
여행 날짜별로 실제 방문 예정 장소의 순서와 동선을 관리하는 확정 일정 계층.
STOBEE
현재 GPS 주변의 장소를 검색·추천하는 AI 챗봇이자, 자체 검색의 장소 상세와 나의 지도를 함께 제공하는 공통 지도 화면.
기록
STOG 카메라 촬영 후 위치와 함께 남기는 사진 및 텍스트 메모. 공개 여부에 따라 발견 피드와 연결 가능.
발견
공개된 STOG 기록과 일반 게시물을 인스타그램형 피드로 소비하는 SNS 영역.
STOG 자체 장소 검색
사용자가 장소명·지역·카테고리 등으로 자체 장소 DB를 조회하는 일반 검색. 결과는 STOBEE와 공유하는 지도 화면의 장소 상세로 연결한다.
여행 기록 세션
사용자가 여행 기록 시작을 눌러 활성화하고 직접 중지·종료하는 위치 기록 단위. 화면이 꺼져도 기록을 이어가는 것이 요구사항이다.
외부 링크 장소 가져오기
공유·붙여넣기로 URL을 받아 백엔드에서 원문 후보를 확인하고 Place로 대조한 후 사용자가 여행 바구니에 저장하는 공통 흐름. Instagram 우선.
추출 후보 / 실제 장소
캡션에서 발견한 이름·주소·근거는 후보이며, 지도에 표시 가능한 내부 Place 연결과는 다른 상태다.

4. 화면 기능 정의
4.1 홈
목적
사용자가 앱을 실행했을 때 현재 활동 상태, 개인 지도 진행도, 관광 콘텐츠, 진행중/예정 여행을 빠르게 확인하는 요약 화면.
화면 구성
상단 헤더: 왼쪽 STOG 로고, 오른쪽 검색 아이콘과 알림 아이콘을 순서대로 배치한다.
헤더 하단 배너: 사용자 이름과 인삿말, 이미지 배경을 활용한 배너 영역.
배너 하단 지표: 활성화한 CELL 수, 나의 여행 수(일상 제외)를 아이콘과 함께 표시.
중앙: 관광 정보 데이터를 활용한 수평 이미지 슬라이드 카드.
하단 “내 여행” 영역: 진행중 여행을 우선, 그 다음 예정 여행 순으로 카드 목록 표시.
주요 동작
검색 아이콘을 누르면 STOG 자체 장소 검색 페이지로 이동한다. 검색 결과에서 장소를 선택하면 STOBEE 지도 화면의 장소 상세 모드로 진입한다.
하나의 Place에 연결되는 홈 관광지 카드는 5.8절의 공통 지도·장소 상세로 연결한다. 여러 장소 행사·지역 소개 등 단일 Place가 아닌 콘텐츠의 상세 목적지는 미확정으로 유지한다.
홈의 여행 카드를 선택하면 일반 여행 상세 페이지가 아니라 “지도 중심 여행 실행 화면”으로 진입한다.
지도 중심 여행 실행 화면은 지도 위에 일정 마커/동선을 보여 주고, 지도 조작을 막지 않는 하단 바텀시트에 여행 이름·날짜 슬라이드·장소 순서를 표시한다.
구현 규칙
나의 여행 수는 진행중·예정·지난 여행을 포함한 “여행”만 계산하며 일상 기록은 제외한다.
여행 상태 정렬 기준은 현재 날짜를 기준으로 진행중 → 예정 순으로 노출한다.
홈 여행 카드와 내 여행 카드의 데이터 원본은 동일하되, 클릭 후 진입 경로는 다르게 처리한다.
핵심 검수 기준
사용자 이름, CELL 수, 여행 수가 서버 데이터와 일치한다.
관광 정보 카드가 가로 스크롤로 자연스럽게 동작한다.
홈 여행 카드 선택 시 지도/바텀시트 조합 화면으로 진입하며 일정 마커와 연결 동선이 보인다.
홈 검색 → 검색 결과 → 선택 장소 지도/상세 흐름이 동작하며, 뒤로 가면 기존 검색어와 결과 목록이 복원된다.
4.2 STOG 카메라 및 CELL 기록
목적
사용자가 실제 장소에서 촬영한 사진과 여행 기록 세션에서 확인한 방문을 지도에 축적하여 개인화된 여행 지도를 만드는 핵심 기능.
화면 구성
CameraX 기반 자체 촬영 화면.
촬영 후 기록 작성 화면: 사진, 텍스트 기록, 공개/비공개 설정.
지도: 사진이 있는 CELL은 대표 이미지를 렌더링하고, 방문만 확인된 CELL은 사진 없이 활성 상태를 표시한다.
CELL 상세 바텀시트: 상단에 사용자 친화적인 위치명, 중앙에 최신순 사진 슬라이드, 하단에 기록 내용을 표시한다. 사진이 없는 CELL에는 사진 없음 상태를 표시하며, 시트 밖 지도는 계속 조작할 수 있다.
주요 동작
촬영 → 기록 작성 → 저장 순으로 진행하며 사진의 촬영 위치·시각을 함께 보관한다. 업로드가 지연되더라도 촬영 당시 위치를 기준으로 기록한다.
사진과 촬영 위치를 기기에 먼저 보관하고 서버 저장·판정 후 해당 CELL 활성화를 확정한다. 오프라인에서는 전송 대기 상태를 유지하며, 새 CELL의 최종 확정은 동기화 후 이루어진다.
사용자가 여행 기록 시작을 눌러 활성화한 세션에서 휴대폰 위치로 방문이 확인되면 CELL을 활성화한다. 여행 날짜가 되었다는 이유만으로 기록을 시작하지 않으며, 사진이 없는 CELL도 이미지 없이 렌더링한다.
같은 CELL에 사진이 여러 장이면 조회자가 볼 수 있는 사진 중 가장 최근 사진을 대표 이미지로 사용하고, 상세 시트에서도 최신순으로 보여 준다.
CELL을 누르면 해당 CELL의 사진과 기록을 상세 시트에서 확인한다. 나의 지도 ON/OFF와 지도 조작은 기록 세션의 시작·중지·종료와 별개다.
공개로 선택한 사진은 발견 게시물로 활용한다. 여행에 연결된 비공개 사진은 작성자와 해당 여행 구성원이 열람할 수 있지만, 발견 피드와 일반 공개 지도에는 노출하지 않는다. 여행과 무관한 개인 비공개 기록은 본인만 열람한다.
구현 규칙
CELL 활성화 정책의 기준은 이 절이다. 본인 STOG 카메라 기록 저장 또는 활성 여행 기록 세션의 방문 확인에만 적용한다. 갤러리·장소 검색·Instagram 등 링크 가져오기·바구니 저장은 활성화나 방문 EXP 사유가 아니다.
지도에 위도·경도 숫자를 그대로 노출하지 않고 주소/장소명 등 사용자 친화적인 위치명으로 변환한다.
CELL 계산에는 서버 h3-java를 사용한다. H3 해상도 10을 초기 검증값으로 사용하며, 앱은 서버가 전달한 GeoJSON과 사진을 Mapbox 레이어로 표시한다. 확정 저장 해상도는 줌과 분리한다. 상세 기준은 6.5절을 따른다.
사진의 실제 GPS 고도를 정확히 측정해서 건물 높이에 붙이는 것을 전제하지 않는다. 위도·경도 기록을 기준으로 Mapbox의 지면/건물 높이 정보를 활용해 시각적 높이를 보정하는 구조를 사용한다.
핵심 검수 기준
촬영한 사진·위치가 기기에 보관되고 서버 동기화가 완료되면 동일 CELL이 활성 상태로 유지된다. 전송 대기 상태를 확정된 CELL 집계와 구분한다.
같은 CELL에 2장 이상 저장했을 때 대표 이미지는 최신 사진이며, 상세 슬라이드는 최신순이다.
여행 비공개 사진은 해당 여행 구성원이 열람할 수 있으며, 비구성원의 조회와 공개 피드 노출은 차단된다.
갤러리 등록·검색·바구니 저장으로 CELL 수가 증가하지 않는다. 사진 없는 CELL에 사진을 추가해도 동일 CELL은 중복 집계하지 않는다.
CELL 데이터 원칙
CELL은 “방문한 위치의 시각적 흔적”을 나타내는 개인 기록 단위다. 동일 위치에 기록을 계속 추가해도 CELL 개수는 최초 활성화 시 1회만 증가하고, 내부 기록 개수는 별도로 증가할 수 있다.
4.2.1 여행 기록 세션
사용자가 기록 시작을 누르면 선택 여행에 연결된 기록 세션을 활성화한다. 화면을 꺼도 세션을 이어가며, 사용자가 직접 중지·종료할 수 있어야 한다.
중지·종료 이후 측정된 새 위치는 방문 기록에 추가하지 않는다. 중지 전에 유효하게 수집한 미전송 샘플은 이후 동기화할 수 있다. 나의 지도 OFF는 표시만 끄며, 위치 기록 종료로 취급하지 않는다.
방문 판정은 위치 품질과 후보 CELL의 연속성을 검사한다. 초기 정확도·측정 시각·연속 확인 기준은 6.6절의 실험값을 따른다. 재개 UI, 종료일·겹치는 여행·강제 종료 이후 정책은 12절에서 별도로 확정한다.
검수: 촬영 없이도 활성 세션의 방문 CELL이 남고, 중지·종료 후 측정된 위치는 제외되며, 화면 잠금 전후 기록이 유지되는지 실기기로 확인한다.
4.3 내 여행
목적
여행 생성부터 협업, 장소 수집, 날짜별 일정 작성, 동선 최적화까지 여행 계획의 중심이 되는 화면.
화면 구성
여행 생성 입력: 여행 이름, 대표 이미지(여행 프로필), 기간, 여행 지역.
내 여행 목록: 진행중 / 예정 / 지난 여행으로 구분.
여행 상세 상단: 대표 이미지, 여행 이름, 기간, 참여 인원.
여행 상세 중단: 여행 바구니 수평 슬라이드.
여행 상세 하단: 날짜 버튼 수평 슬라이드 + 선택 날짜의 일정 리스트.
여행 카드/일정 선택 상태에 따라 바구니와 일정 사이에 지도 영역을 표시할 수 있는 레이아웃.
주요 동작
여행 생성 후 상세 화면에서 여행 정보를 수정할 수 있다.
여행 생성 시 일정 선택은 Date Picker를 사용
더보기 메뉴에서 여행 삭제, 대표 이미지 변경, 이름 변경, 링크 초대를 제공한다.
초대 링크를 받은 사용자는 유효기간 내 참여하면 동일 여행 데이터를 함께 수정하고 공유한다. 초대 링크의 유효기간은 서버 발급 시점부터 10분이다.
Instagram 공유 또는 링크 붙여넣기로 장소 후보를 가져오고, 사용자가 장소와 대상 여행을 확인해 기존 여행 바구니에 저장한다. 카카오·네이버 지도 공유는 후속 구현한다. 공통 저장은 5.4절, 상세 추출은 14절을 따른다.
여행 바구니 장소 카드의 + 버튼으로 동일 TripItem을 선택 날짜의 일정 상태로 이동한다. 복사하지 않으며, 서버 성공 후 바구니 목록에서는 제거한다. 바구니와 일정은 화면상 두 계층을 유지한다.
일정 카드의 X 버튼을 누르면 “여행 바구니로 이동” 또는 “삭제”를 선택하는 확인 모달을 표시한다.
일정 카드 순서를 위/아래로 변경할 수 있고 카드·지도 마커에 동일 번호를 표시한다. 드래그 중에는 앱에서 미리 보여 주며, 드래그 종료 시 최종 순서를 한 번 전송한다.
하단 동선 짜기 버튼은 선택 날짜의 장소와 음식점 정보를 바탕으로 변경안을 생성한다. 사용자가 변경안을 확인하고 적용해야 기존 일정에 반영하며, 취소하면 기존 일정을 유지한다.
구현 규칙
여행 삭제는 관리자만 가능하다. 관리자는 여행 나가기를 사용할 수 없으며, 여행에서 빠지는 대신 여행 삭제만 가능하다. 일반적인 여행 편집 권한은 그대로 유지한다.
일반 구성원에게는 더보기의 여행 나가기 기능을 제공한다. 관리자에게는 나가기 기능을 제공하지 않고 서버에서도 거부한다.
초대된 구성원은 여행 정보, 바구니, 일정 내용을 함께 수정할 수 있다.
여행 바구니와 여행 일정의 두 계층 UX는 유지한다. DB에서는 동일 TripItem의 일정 날짜·순서 상태를 바꿔 이동을 표현한다. 일정 X의 여행 바구니 선택은 반대 방향 이동이다.
여행 상태는 날짜 기준으로 분류한다: 시작일 ≤ 현재일 ≤ 종료일이면 진행중, 현재일 &lt; 시작일이면 예정, 종료일 &lt; 현재일이면 지난 여행.
외부 공유 유입은 Instagram을 우선 구현하고, 이후 카카오·네이버 지도 공유 어댑터를 추가한다. 플랫폼별 추출 이후의 Place 대조·여행 선택·바구니 저장은 공통 처리한다.
핵심 검수 기준
여행 생성 후 상태 분류가 날짜에 따라 정확히 적용된다.
관리자가 아닌 구성원에게 여행 삭제 기능이 노출되지 않거나 실행이 거부된다.
바구니에서 일정으로 이동하면 선택 날짜에 반영되고 원래 바구니 항목은 남지 않는다. 실패 시 양쪽에서 모두 사라지지 않아야 한다.
일정 순서 변경 후 카드 번호·지도 마커 번호·동선 순서가 일치한다.
같은 여행을 두 사용자가 열었을 때 수정 결과가 서버 기준으로 동기화된다.
관리자는 나가기 불가·삭제 가능, 일반 구성원은 나가기 가능·삭제 불가가 UI와 서버에서 동일하게 적용된다.
초대 링크는 서버 발급 후 10분이 지나면 신규 참여를 거부한다. 이미 참여한 구성원의 소속은 링크 만료만으로 취소하지 않는다.
동선 변경안 확인 전에는 원래 일정이 바뀌지 않고, 적용 후에만 카드 번호·마커·동선이 함께 변경된다.
4.3.1 여행 바구니 카드
영역
요구사항
헤더
저장한 사용자의 프로필 이미지와 이름을 표시. 오른쪽 끝 X 삭제 버튼.
이미지
장소를 대표하는 이미지가 카드의 주요 시각 요소로 노출.
하단
장소 이름 + 오른쪽 + 버튼. 선택 날짜 일정으로 이동하며 성공 후 바구니에서 제거.
삭제
X 선택 시 즉시 삭제하지 않고 확인 모달을 거친다.
4.3.2 여행 일정 카드
요소
요구사항
순서번호
TRIPPLE 앱과 유사하게 일정 순서를 숫자로 표시하며 지도 마커와 동일 번호 사용.
장소 정보
장소 이름 + 하단 주소.
삭제/이동
오른쪽 X → 확인 모달 → 여행 바구니로 이동 또는 삭제. 복사본은 만들지 않는다.
순서 변경
앱에서 순서를 미리 표시하고 드래그 종료 또는 조작 완료 시 최종 항목 순서와 plan_version을 한 번 전송. 서버는 소속·중복·누락을 검증.
4.3.3 외부 공유 링크 → STOG 바구니
1. Android 공유 수신 또는 앱 내부 링크 붙여넣기로 외부 URL을 받는다. Instagram을 먼저 지원하고, 카카오·네이버는 후속 지원 상태로 구분한다.
2. URL을 검사해 제공자를 식별한다. Instagram은 캡션 확보 → 후보 분리의 비동기 경로로 처리하며, 후속 지도 링크는 제공자별 식별자·이름·주소 추출 경로를 사용한다.
3. 자체 Place DB를 우선 대조하고 필요한 후보만 승인된 무료 외부 검색으로 보완한다. 후보·근거와 미확정 상태를 보존하며 첫 검색 결과를 자동 확정하지 않는다.
4. 사용자에게 저장할 장소를 확인받는다. 진행중·예정 여행을 선택하되 여행 바구니에서 진입한 경우 해당 여행을 유지한다. 복수 장소는 사용자가 선택한 항목만 처리한다.
5. 확인된 장소를 5.4절의 공통 저장 처리로 TripItem 바구니 상태에 넣는다. 저장 사용자·출처를 연결하고 커밋 후 기존 SSE로 구성원에게 변경을 알린다. 추출 완료와 저장 완료는 구분한다.
최신 1차 지원 우선순위Instagram 공유 링크 → 후보 확인 → 여행 바구니의 전체 흐름을 먼저 구현한다. 카카오·네이버 지도 공유는 이후 동일한 저장 처리에 어댑터를 추가한다. 두 URL의 로컬 검증은 보고된 사실이며 서버 성공률·장소 매칭 완료 보장은 아니다.
4.3.4 동선 변경안과 기간 변경
동선 짜기 → 변경 전/후 확인 → 적용 또는 취소 순으로 진행한다. 좌표 기반 후보 순서를 먼저 좁힌 후 선택 후보의 연결 구간만 실제 경로를 조회한다. TMAP 도보 우선 검증과 상세 조건은 6.7절을 따른다.
변경안에는 생성 당시 plan_version을 포함한다. 적용 시 서버 최신 버전과 다르면 오래된 변경안을 덮어쓰지 않고 충돌을 안내한 뒤 재계산한다. 적용은 버전 검사와 같은 트랜잭션에서 처리한다.
여행 기간 단축으로 범위 밖이 되는 일정의 이동·보존 정책은 미확정이다. 12절의 제안은 승인 전 구현 규칙으로 취급하지 않는다.
4.3.5 Instagram 가져오기 화면
외부 공유로 진입하거나 여행 바구니 제목 옆 “장소 추가”에서 “Instagram 링크 가져오기”를 선택한다. 같은 장소 추가 진입에서 자체 장소 검색도 재사용한다. 새 하단 탭·Instagram 피드·개인 장소 보관함은 추가하지 않는다.
화면 상태
요구사항
입력·로그인
URL 또는 공유 텍스트를 확인한다. 인증이 없으면 로그인 후 입력을 복원하며 로그인 전 자동 브라우저 작업을 시작하지 않는다.
처리 중
작업 ID로 대기·캡션 확인·장소 대조 단계를 표시한다. 검증되지 않은 퍼센트나 성공을 미리 표시하지 않는다.
결과 확인
장소별 이름·원문 주소/지역·근거·연결 후보를 표시한다. 주소 없음, 비교 미확인, 연결 실패를 별도 안내한다.
장소 선택·저장
사용자가 확인한 장소만 저장한다. 연결이 모호하면 공통 장소 검색으로 대조하고 원문을 덮어쓰지 않는다.
실패·복귀
접근 실패·캡션 없음·후보 없음·장소 미해결을 구분한다. 본문 붙여넣기 보조는 user_input 출처로 표시하며 자동 수집 성공으로 집계하지 않는다.
화면 재진입
작업 상태와 선택 상태를 복원한다. 지도로 잠시 이동해도 작업 ID·후보 목록을 보존하고, 화면을 나가면 상태 폴링을 멈춘다.
검수: Instagram 링크 하나에서 복수 장소를 추출해도 사용자 확인 전 바구니·일정·CELL·발견 게시물은 바뀌지 않는다. 선택 장소만 저장되고 같은 요청 재시도로 복제되지 않는다. 구현 계약은 14절을 기준으로 한다.
4.4 STOBEE
목적
현재 GPS 주변의 장소를 대화로 탐색하는 AI 보조 기능이며, 자체 검색의 장소 상세와 ON/OFF 가능한 나의 지도를 제공하는 공통 지도 화면이다.
화면 구성
상단 헤더는 앱 공통 헤더 라인을 유지한다.
배경은 지도이며, STOBEE 탭으로 진입하면 현재 위치를 중심으로 사용자 위치와 바라보는 방향을 표시한다. 자체 검색으로 진입하면 선택 장소를 중심으로 표시한다.
지도 위에 나의 지도 ON/OFF 제어를 제공한다. ON은 본인이 활성화한 CELL과 기록을 표시하고 OFF는 해당 레이어만 숨긴다. 기본값과 버튼의 정확한 위치는 추후 확정한다.
오른쪽 카메라 버튼 대신 STOG 아이콘 버튼을 배치한다. 버튼을 누르면 하단 내비게이션 바로 위에 채팅 입력창을 포함한 바텀시트를 연다.
채팅 바텀시트는 완전히 닫을 수 있으며, 오른쪽 STOG 아이콘 버튼으로 다시 연다.
자체 검색에서 장소를 선택해 진입하면 채팅창 대신 장소 상세 바텀시트를 표시한다. 장소 선택만으로 AI 대화를 자동 시작하지 않는다.
입력 시 키보드와 함께 채팅 시트를 확장하되 상단 헤더를 침범하지 않는다. 시트가 열려 있어도 노출된 지도 영역은 이동·확대·축소할 수 있어야 한다.
추천 결과는 채팅 안에서 최대 5개의 장소 카드로 표시하고, 동일 장소를 지도 위 마커로 함께 표현한다.
장소 상세 시트에는 대표 이미지, 장소명, 카테고리, 주소와 여행 바구니 저장·길찾기 버튼을 배치한다.
주요 동작
사용자 질문에 주변 장소와 추천 근거를 제시한다. “근처 식당”은 현재 GPS 기준이다. 이 규칙을 Instagram 캡션의 장소 대조에 전용하지 않는다. Instagram은 캡션의 지역·주소를 우선하고 불명확하면 사용자 확인을 요청한다.
추천 카드의 바구니 아이콘은 5.4절의 공통 장소 저장을 호출한다. 진행중·예정 여행을 선택하며, 이미 유효한 여행 문맥이 있으면 해당 여행을 유지한다.
바구니 아이콘 옆 길찾기 아이콘을 제공하여 지도에 현재 위치부터 해당 장소까지의 동선을 표시한다.
지도를 확대하면 발견에 공개된 다른 사용자의 위치 기반 사진을 육각형 마커로 표시한다. 나의 지도와 공개 기록의 조회·표시 범위를 구분하고 줌 배율에 따라 렌더링 범위를 나눈다.
다른 사용자의 공개 기록 마커를 누르면 해당 게시물을 지도 위 상세 카드/시트에 표시하며 X로 닫는다. 노출된 지도 영역의 조작을 막지 않는다.
장소 상세·채팅은 5.8절의 공통 단일 시트 상태를 따른다. STOG 버튼 선택 시 장소 상세를 접고 채팅을 열며 두 시트를 중첩하지 않는다.
구현 규칙
장소 추천 카드는 한 응답에 최대 5개로 제한한다.
시트 내부 스크롤·드래그와 지도 이동·줌의 터치 영역을 분리한다. 지도와 함께 쓰는 시트는 배경 지도 조작을 차단하는 모달로 구현하지 않는다.
일반 공개 지도에는 공개 기록만 표시한다. 본인의 비공개 기록과 해당 여행 구성원의 열람 권한은 5.5절을 따르며 공개 데이터 응답에 섞지 않는다.
추천 근거는 실제 사용한 장소 정보·사용자 질문·거리/상황 등 설명 가능한 정보 범위에서 제시한다.
검색에서 진입한 지도 화면의 뒤로 가기는 기존 검색 페이지로 연결한다. 검색어·결과 목록·스크롤 위치를 유지한다.
핵심 검수 기준
채팅 입력 시 키보드가 올라와도 입력창과 메시지가 가려지지 않는다.
추천 카드와 지도 마커가 동일 장소를 가리킨다.
여행 바구니 저장은 진행중/예정 여행만 선택 가능하다.
나의 지도에서는 본인의 비공개 기록을 볼 수 있지만, 비구성원의 공개 지도 응답에는 여행 비공개 사진이 포함되지 않는다.
검색 진입 시 선택 장소의 마커와 상세 정보가 일치하고, AI는 사용자가 실행 버튼을 눌렀을 때만 열린다.
나의 지도 ON/OFF를 전환해도 실제 CELL 수·경험치·여행 기록 세션 상태는 변하지 않는다. 지도 배율 변경으로 동일 CELL이 중복 집계되지 않는다.
지도 중심을 다른 지역으로 옮긴 상태에서도 “근처” 요청은 현재 GPS를 기준으로 처리한다. GPS를 얻지 못하면 위치 확인 상태를 안내하고 임의의 기준으로 대체하지 않는다.
4.5 발견
목적
STOG 안에서 공개된 위치 기반 기록과 일반 게시물을 다른 사용자와 공유하고, 장소를 다시 여행 계획으로 연결하는 SNS 피드.
화면 구성
상단 헤더: 왼쪽 + 아이콘, 중앙 “발견”, 오른쪽 하트 아이콘.
+ 선택 시 갤러리 사진을 선택해 일반 게시물을 작성할 수 있는 등록 화면으로 이동.
하트 선택 시 사용자가 좋아요를 누른 게시물만 모아보는 화면으로 이동.
피드는 카드 컨테이너 없이 인스타그램과 유사한 세로형 게시물 레이아웃.
게시물 상단: 사용자 프로필과 사용자 이름.
사진 영역: 하나 이상일 경우 수평 슬라이드.
사진 하단: 좋아요, 댓글, 오른쪽 끝 여행 바구니 저장 아이콘.
그 아래 사용자 이름 + 게시물 텍스트 + 날짜.
주요 동작
좋아요, 댓글, 여행 바구니 저장 기능을 제공한다. 여러 장소가 포함된 게시물에서 저장할 장소는 사용자가 선택하며, 전체 장소나 현재 슬라이드 장소를 자동 저장한다고 전제하지 않는다.
댓글 아이콘 선택 시 댓글 목록을 바텀시트로 표시한다.
댓글은 사용자 프로필, 이름, 댓글 내용으로 구성하며 프로필 선택 시 해당 사용자 프로필로 이동한다.
게시물의 개별 사진을 누르면 화면을 회색 오버레이 상태로 전환하고 중앙의 원형 위치 아이콘을 표시한다.
위치 아이콘 선택 시 해당 사진의 기록 위치를 중심으로 하는 지도 화면으로 전환하고 마커를 표시한다.
구현 규칙
게시물 종류는 ① 일상: STOG 카메라 단일 사진, ② 여행 사진: 여행 기간 기록 중 사용자가 공개 대상으로 선택한 여러 사진, ③ 일반 게시물: 발견 +에서 갤러리로 등록한 게시물의 세 가지로 구분한다.
여행 사진 게시물은 여행 중 촬영한 모든 기록을 강제 공개하지 않고 사진별 공개 선택 결과를 따른다.
사진별 공개 선택과 사진별 위치 이동은 유지한다. 작성자의 공개 사진 선택, 열람자의 저장 장소 선택, Instagram 후보 확인은 서로 다른 선택이다. 저장 자체는 공통 5.4절을 사용한다.
위치 정보가 없는 일반 갤러리 게시물은 지도 위치 이동 기능을 비활성 또는 미노출 처리한다.
핵심 검수 기준
여행 비공개 사진을 구성원끼리 열람할 수 있어도 발견 피드에는 사용자가 공개로 선택한 사진만 표시된다.
멀티 사진 게시물은 좌우 슬라이드가 정상 동작한다.
댓글 바텀시트에서 사용자 프로필 이동이 가능하다.
게시물에서 사용자가 선택한 장소만 선택 여행의 바구니에 들어간다. 게시물 전체 장소를 일괄 저장하지 않는다.
4.6 MY
목적
사용자 활동을 프로필, 레벨, 지도 채움 정도, 여행/좋아요 수, 게시물 그리드로 요약하는 개인 영역.
화면 구성
상단 프로필: 변경 가능한 프로필 이미지, 사용자 이름, 이름 아래 현재 레벨과 단계 수식어.
활동 지표: 활성화 CELL 수, 여행 수, 좋아요 수. 별도 카드 컨테이너 없이 간결하게 배치.
하단: 인스타그램과 유사한 3열 게시물 그리드.
주요 동작
프로필 이미지 변경.
게시물 그리드 선택 시 해당 사용자의 게시물만 이어지는 피드/게시물 화면으로 진입.
나의 지도는 별도 MY 지도 페이지가 아니라 STOBEE 배경 지도에서 ON/OFF하여 확인한다. MY의 기존 지표·그리드 구성은 유지한다.
CELL 최초 활성화와 사진 촬영 기록 등록 활동에 따라 경험치를 부여하고 레벨을 계산한다.
구현 규칙
레벨은 1~100 범위를 사용한다.
레벨 10 단위로 10개 단계 수식어를 둔다.

4.7 STOG 자체 장소 검색
목적
외부 지도 앱이나 AI 대화를 거치지 않고 STOG 내부에서 장소를 직접 검색하고, 지도에서 확인한 뒤 여행 바구니에 연결한다.
화면 구성
검색 페이지: 뒤로 가기, 검색 입력창, 입력 내용 초기화 X, 검색 결과 리스트를 배치한다.
검색 결과: 장소 대표 이미지, 장소명, 카테고리, 주소/지역을 표시한다. 이미지나 부가정보가 없으면 대체 상태로 표시한다.
지도 상세는 5.8절의 기존 STOBEE 공통 지도·장소 상세를 재사용한다. 검색 전용·Instagram 전용 지도 SDK 화면을 따로 만들지 않는다.
주요 동작
홈 검색 아이콘 → 자체 장소 검색 페이지 → 검색어 입력 → 검색 결과에서 장소 선택 순으로 이동한다.
장소 선택 → 선택 장소 중심 지도/마커 → 장소 상세 바텀시트 순으로 표시한다. 이 단계에서는 AI 채팅이 열리지 않는다.
장소 상세의 바구니 버튼은 5.4절의 공통 저장을 호출한다. 홈 검색 진입은 여행을 선택하고 여행 바구니 진입은 기존 여행 문맥을 유지한다. 길찾기는 현재 위치부터 선택 장소까지 표시한다.
AI 탐색이 필요하면 STOG 아이콘 버튼으로 장소 상세를 접고 채팅 시트를 연다. 검색으로 돌아가면 검색어·결과·스크롤 위치를 유지한다.
구현 규칙
검색은 STOG 서버의 통합 Place를 기준으로 한다. 장소명 정규화·pg_trgm 검색과 지역·카테고리 조건을 결합하고 필요한 필드와 결과 수만 반환한다. 세부 정렬·짧은 검색어·초성 검색 정책은 별도로 확정한다.
자체 검색은 일반 장소 조회이며 STOBEE의 AI 추천과 구분한다. AI 추천 카드의 최대 5개 제한을 일반 검색 결과에 적용하지 않는다.
검색 또는 바구니 저장만으로 CELL을 활성화하지 않는다. CELL 활성화는 별도의 기록 규칙을 따른다.
검색 결과 없음, 네트워크 오류, 좌표/이미지 부족 상태를 구분한다. 여행 바구니 “장소 추가”의 자체 검색 진입은 채택한다. 최근 검색어·자동완성·추가 진입 위치는 미확정이다.
핵심 검수 기준
검색 결과·지도 마커·장소 상세·바구니 항목이 동일한 Place를 참조한다.
검색 결과 선택만으로 AI 요청이 발생하지 않으며, 장소 상세와 채팅 시트가 중첩되지 않는다.
지도에서 뒤로 가기를 누르면 기존 검색 결과를 이어서 탐색할 수 있다.

5.3 동기화 원칙
여행 협업 데이터의 기준 원본은 서버의 PostgreSQL 데이터로 둔다.
장소 추가·삭제·이동·순서 변경은 REST API로 처리한다. 서버는 계획 버전과 권한을 검사하고 DB 커밋 후 해당 여행 구성원에게 SSE로 변경 사실을 전달한다.
앱은 SSE 수신 후 REST API로 최신 데이터를 재조회한다. 알림에는 여행 ID·변경 버전·변경 범위만 보내며 전체 사진·여행 데이터를 넣지 않는다. 초기 WebSocket은 제외하고, 연결·조회마다 JWT와 여행 구성원 권한을 검사한다.
SSE는 필요한 여행 화면에서 구독하고 비활성 연결은 정리한다. 재연결·화면 재진입 시 서버 최신 상태를 다시 읽으며, 짧게 연속된 알림은 최신 버전 기준으로 재조회를 합친다. SSE 유실 복구용 영구 이벤트 저장소는 초기 도입하지 않는다.
구현: Spring MVC SseEmitter + OkHttp SSE 모듈을 사용한다. @TransactionalEventListener의 커밋 이후 단계에서 알림을 발생시키며, 재연결·인증 만료·프록시 타임아웃·연결 정리는 구현 검증 항목이다. [E9][E21][E23]

복수 장소는 사용자가 선택한 항목만 저장한다. 후보 단계와 실제 Place 연결을 구분하고, 좌표를 확인하지 못한 후보를 현재 GPS나 임의 좌표의 정식 Place로 만들지 않는다.
요청에는 target trip, place 식별 또는 검증된 후보 선택, source reference, request_id, expected_plan_version을 포함한다. 실제 이름은 API 계약과 맞춘다. 네트워크 재시도 중복과 의도적 같은 장소 반복 저장 정책은 분리한다.
저장 성공 시 TripItem은 날짜·순서가 없는 바구니 상태다. 바구니 → 일정 이동은 8.1절을 따른다. 추출/검색만으로 일정에 바로 넣지 않으며 CELL·촬영 Record·EXP·발견 Post를 만들지 않는다.
링크는 장소 유입의 출처일 뿐 사진·영상 재게시 기능이 아니다. 외부 사진을 STOG 촬영 기록으로 취급하지 않고, 썸네일이 없으면 기존 장소 이미지 또는 대체 상태를 사용한다.

5.6 초대 링크 정책
초대 링크는 발급 시각부터 10분간 유효하고 서버 시각으로 만료를 판정한다. 만료 후 신규 참여는 거부한다. 링크 만료는 이미 참여한 구성원의 소속 기간을 뜻하지 않는다.
링크 재발급 시 기존 링크 폐기 여부, 1회/다회 사용, 관리자 이외 구성원의 발급 권한 세부 정책은 미확정이다. 기존 초대 링크 공유 가능 권한은 유지한다.
5.7 동시 편집과 재시도 일관성
여행 계획 전체를 하나의 버전 단위로 관리한다. 단순한 “마지막 요청 우선” 덮어쓰기나 서로 다른 순서 변경의 자동 병합은 사용하지 않는다. 날짜별 버전 분리는 불필요한 충돌이 실제로 자주 관측될 때 검토한다.

갱신 행이 없으면 권한·존재 여부를 재검증한 뒤 버전 충돌을 구분한다. 계획 변경에 실패하면 버전 증가도 함께 롤백한다.
바구니·일정 이동·재정렬·계획에 영향을 주는 기간 변경은 같은 계획 버전 기준을 따른다. 사진 업로드·좋아요·경험치까지 계획 버전을 증가시키지 않는다.
여행 단위 버전에서는 서로 다른 날짜를 수정해도 충돌할 수 있다. 초기 복잡도를 줄이기 위한 선택이며, 충돌 빈도를 측정한 뒤 세분화를 검토한다.
5.7.2 중복 요청과 원자적 이동
생성·이동 등 수정 요청에 request_id를 붙인다. 저장 성공 뒤 응답이 유실되어 동일 요청이 재전송되어도 같은 작업을 중복 실행하지 않는다. 성공 상태와 재응답 정보를 DB 커밋과 일관되게 관리한다.
미전송 위치는 기록 세션 ID와 샘플 순번으로 식별한다. 동일 위치 묶음 재전송이 CELL·경험치 중복 지급으로 이어지지 않도록 한다.
TripItem의 일정 날짜와 순서를 변경해 바구니 ↔ 일정 이동을 처리한다. 실패하면 기존 상태를 유지하며, 두 위치에 복사본을 남기거나 양쪽에서 모두 삭제하지 않는다.
재정렬은 조작 완료 시 한 번 저장한다. 서버에서 모든 항목의 여행·날짜 소속, 중복·누락을 확인하고 정수 순서를 같은 트랜잭션에서 부여한다.
역할 구분: plan_version은 덮어쓰기 방지, request_id는 재시도 중복 방지, 트랜잭션은 중간 상태 방지, SSE는 커밋된 변경의 전달을 담당한다.
5.8 공통 지도·장소 상세·시트
검색, 단일 Place 관광 카드, STOBEE 추천, Instagram 확인 후보의 지도 보기에서 같은 지도·장소 상세를 재사용한다. 일반 검색과 AI 입력, 홈 실행 화면과 내 여행 편집 화면의 역할 차이는 유지한다.

사용자가 고른 실제 Place 후보의 위치를 확인한다. 돌아가면 원문 근거·작업 ID·선택 상태 유지. 미해결 장소에 가짜 마커를 만들지 않음.
STOBEE 대화
현재 GPS 주변 추천. 장소 상세와 채팅은 단일 시트 상태로 전환하고 헤더를 침범하지 않음.
나의 지도 / 여행 실행
CELL·사진 또는 날짜별 일정 정보를 중심으로 표시한다. 선택한 대상에 맞는 상세만 열고 모든 패널을 동시에 펼치지 않음.
지도와 함께 쓰는 시트는 CoordinatorLayout + BottomSheetBehavior 방향으로 구성한다. 시트 내부 스크롤·드래그 영역과 시트 밖 지도의 이동·줌 영역을 구분한다. 저장/삭제 확인 대화상자 등 의도적인 모달은 별개다. [E8]
높은 사진 Billboard·건물 위 Z축 연출은 기본 CELL 사진 표시를 대체하지 않는 선택적 검증 항목이다. 새 탭·새 기록 저장소를 추가하지 않는다. Rain/Snow 렌더링은 6.1절에 따라 제외한다.

높이 표현
스마트폰 GPS 고도 기반 층수 판별은 제외. 지도 지면·건물 높이 보정은 선택적 표현 검증이며 CELL을 채우는 사진 표시를 대체하지 않는다.
6.2 위치 정보 처리
LocationManager를 사용해 촬영/현재 위치를 획득한다. 다른 위치 API로 교체할 필요가 생기면 프로젝트 제약과 정확도를 기준으로 재검토한다.
사진 기록에는 위도·경도를 내부 데이터로 저장하되 사용자 화면에는 장소명/주소 형태로 표현한다.
CELL 식별은 서버 H3, 주변·영역 조회는 PostGIS로 역할을 분리한다. 앱은 위치 1차 필터와 Room 전송 큐를 담당하고 서버가 방문 판정·CELL 활성화를 확정한다.
6.3 나의 지도 표시와 줌별 렌더링
확정: STOBEE 배경 지도에서 나의 지도를 ON/OFF한다. 지도의 확대 수준과 현재 보이는 범위에 따라 로딩·렌더링 대상을 나누며, 시트가 열려도 지도는 조작할 수 있어야 한다.
표의 범위별 로딩·표시 전략을 채택한다. 줌 경계·사진 수·도형 수 상한은 실기기에서 정하며, 저장된 CELL 해상도와 집계 기준을 줌에 따라 바꾸지 않는다. 요약 영역은 넓은 영역 전체의 방문을 뜻하지 않는다.

6.4 화면이 꺼져도 이어지는 위치 기록
채택: LocationManager + location 유형 Foreground Service를 결합한다. 보이는 화면에서 사용자가 기록을 시작하고 권한을 허용한 뒤 기록 상태 알림을 제공한다. Room은 미전송 샘플 보관, WorkManager는 업로드 재시도에 사용한다. [E6][E7][E17]
화면 꺼짐만을 이유로 백그라운드 위치 권한을 무조건 요청하지 않는다. 서비스 시작 시점·Android 버전별 선언/권한 조건을 맞춰야 하며, 강제 종료·권한 철회·절전 상황까지 무중단을 보장한다고 표현하지 않는다. [E6][E7]
6.5 CELL 인덱싱·저장 및 계산 분담
H3를 CELL 식별 체계로 채택하고 초기에는 서버 h3-java에서 계산한다. 직접 육각 격자를 새로 만들기보다 저장 규칙을 고정하고 조회·이미지 전송량을 줄인다. H3 식별, Mapbox 렌더링, 개별 Place 정보는 별개 역할이다. [E11][E13]

Mapbox 화면
서버 데이터의 도형·사진 표시만 수행. 확대·축소나 조회만으로 CELL을 새로 활성화하지 않는다.
전체 지역의 빈 CELL을 미리 생성하지 않는다. 방문하거나 사진을 남긴 CELL만 활성화 데이터로 저장한다.
사용자별 활성화에는 UNIQUE(user_id, cell_id)를 둔다. INSERT ... ON CONFLICT DO NOTHING 등으로 중복을 막고 실제 최초 삽입 때만 CELL 수와 활성화 EXP를 반영한다. [E14]
CELL 내부 사진과 사진별 Place는 별도 기록으로 누적한다. 대표 사진은 조회자의 열람 권한을 만족하는 최신 사진으로 선택한다.
CELL별로 별도 Android View나 레이어를 생성하지 않는다. Fill·Line·Symbol을 역할별로 조합하고, 지도용 작은 썸네일을 사용한다. [E10]
초기 오프라인 모드는 위치·사진 저장과 재전송을 지원하지만 새 CELL의 최종 확정은 서버 동기화 이후다. 완전한 오프라인 즉시 채움이 별도 요구로 확정되면 앱 내부 H3 계산을 추가 검토한다.
구현 점검: h3-java의 실행 환경·네이티브 바이너리·버전을 서버에서 검증한다. 앱에 추가할 경우 Android ABI와 x86_64 에뮬레이터 지원을 별도로 확인한다. 현재 설계는 Android H3 의존성을 추가하지 않는다. [E13]
6.6 방문 확인·전송 주기
복잡한 위치 보정 모델보다 품질·시간·연속성 검사를 먼저 사용한다. 다음 수치는 STOG 실험 시작값이며 방문을 완벽히 증명하거나 오차를 보장하는 기준이 아니다.

6.7 무료 길찾기와 제한된 동선 계산
초기 우선 검증 제공자는 TMAP이며, 도보부터 검증·연결하고 같은 제공자 안에서 자동차를 확장한다. 제공자 이용 조건, 비용 0원 운영, Mapbox 위 경로 표시 허용, 실제 국내 경로 품질을 확인한 뒤 최종 확정한다. 대중교통은 초기 확정 범위에 포함하지 않는다.
검증 항목
연결 조건
무료 범위·과금
무료 계정·초과 차단·요금 전환 조건을 확인한다. 서버 내부 호출 상한을 제공자 한도보다 낮게 두고 초과 시 길찾기만 제한한다.
경로 데이터 이용
이전 설계안의 검토값은 일 1,000건 무료 및 저장 후 24시간 이상 사용 제한이다. 실제 적용 상품·계정·최신 약관을 재확인하기 전 운영 조건으로 확정하지 않는다. [E18]
지도 혼용
TMAP 결과를 Mapbox 위에 표시하는 사용 방식의 허용 여부를 확인한다. 확인 전 혼용 가능으로 단정하지 않는다.
품질
서비스 대상 지역의 도보·자동차 실제 경로, 소요시간·실패 사례를 시험한다.
대안
조건이 맞지 않을 때 기존 PC에서 제한 지역 GraphHopper 자체 운영을 검토한다. 무료 소프트웨어와 데이터 준비·갱신·메모리 운영 부담은 구분한다. [E19]
길찾기 호출은 서버 한곳으로 모은다. 일별 사용량은 재시작으로 초기화되지 않게 DB에서 관리하고 한도 부족 시 유료 대안으로 자동 전환하지 않는다.
사용자 여행 장소·순서와 외부 경로 응답을 분리한다. 경로·소요시간 캐시는 약관상 허용 기간 안에서만 사용하고, 만료 데이터를 영구 여행 데이터처럼 재사용하지 않는다.
여러 장소의 모든 출발·도착 조합을 외부 경로 API에 보내지 않는다. 좌표 기반으로 가까운 순서를 만들고 제한된 순서 교환으로 개선한 뒤, 소수 후보의 연결 구간만 실제 경로를 조회한다.
후보 수·연산 횟수 또는 실행시간에 상한을 둔다. 고정 일정과 제공된 운영시간을 존중하며, 음식점 삽입·점수 가중치·세부 제약은 별도 확정한다.
직선거리 기반 후보는 실제 도로 최적해가 아니다. 화면에는 동선 개선안으로 제공하고, 길찾기 실패 시 직선을 실제 경로처럼 표시하지 않는다.
동선 후보 계산과 외부 API 대기 동안 DB 트랜잭션을 길게 유지하지 않는다. 사용자의 적용 요청 시 계획 버전을 다시 검사한 뒤 짧은 트랜잭션으로 반영한다.

7.1 데이터 통합 원칙
상가정보 CSV로 기본 상업 장소 목록을 만들고 API는 보조적으로 사용한다.
관광공사 데이터는 서버의 수집 작업 → 자체 PostgreSQL → Android 앱의 지도·검색·추천 순으로 사용한다.
날씨는 장소별로 매번 호출하지 않고 동일 예보 격자 단위로 요청 결과를 공유한다.
여러 데이터 소스가 같은 장소를 제공해도 내부에서는 하나의 장소로 연결하는 중복 제거/매칭 기준을 반드시 둔다.
축제·행사, 숙박, 반려동물 동반여행, 기본 관광지 이미지는 우선 국문 관광정보 서비스 범위로 충족 가능한지 확인한다.
고캠핑·무장애·웰니스는 초기부터 모두 같은 비중으로 적재하지 않고 실제 화면에서 사용할 테마부터 순차적으로 붙인다.

7.3 자체 검색과 공간 조회
PostgreSQL에 PostGIS와 pg_trgm을 채택한다. 별도 검색·공간 서버를 추가하지 않고, 자체 장소 DB의 검색과 현재 GPS·지도 범위 조회를 분리해 최적화한다.

부분 일치·유사도 검색의 출발점. 유효 trigram이 부족한 짧은 검색어는 별도 검증한다. [E26]
지역·업종 결합
지역·카테고리 조건과 장소명 조건 분리
예: 군산 카페는 지역=군산, 카테고리=카페를 함께 고려한다. 초성·의미 검색을 자동 지원한다고 전제하지 않는다.
검색·지도 API는 결과 개수와 필요한 필드를 제한한다. 앱에서 전체 장소 좌표를 내려받아 반경을 계산하는 구조를 사용하지 않는다.
H3는 CELL ID, PostGIS는 거리·영역 조건, pg_trgm은 문자열 검색에 사용한다. 초기에는 Elasticsearch·벡터 DB·Redis를 추가하지 않는다.
EXPLAIN ANALYZE로 실제 실행 계획·인덱스 사용·느린 쿼리를 점검한다. 인덱스 존재만으로 성능 충족을 판단하지 않는다. [E27]
7.4 외부 링크 후보와 기존 Place 연결
Instagram에서 추출한 원문 이름·주소·지역과 기존 Place를 대조한다. 새 Instagram 전용 장소 DB를 만들지 않으며 검색·PostGIS·pg_trgm 모듈을 재사용한다. 현재 GPS는 링크의 지역 근거가 아니다.
외부 장소 검색은 자체 DB 미보유·모호 후보에만 사용한다. 카카오 로컬 API는 키워드 검색·주소 좌표 변환을 제공하지만, 주소 좌표를 찾았다는 이유만으로 특정 업소를 확인한 것으로 처리하지 않는다. API 제공자·저장/지도 표시·무료 조건은 연결 전 검증한다. 카카오 “검색 API 보완” 검토는 카카오 “공유 링크” 후속 개발과 다른 작업이다. [E31]
공용 Place에는 정규화된 장소 데이터와 출처별 연결을 관리한다. 캡션의 address_raw·name_raw·근거는 ImportJob 결과에 별도 보존하며, 사용자 한 명의 수정으로 공용 장소를 즉시 덮어쓰지 않는다. 상세 매칭 계약은 14.6절을 따른다.
8. 핵심 데이터 모델 초안
실제 전체 DDL이 아니라 v1.4의 기능 관계와 채택 저장 방향을 정의한 개념 모델이다. 기존 TripItem·Place·권한 모델을 유지하고 Instagram의 작업·후보·출처만 연결한다. 세부 타입·보관기간·인덱스는 구현 시 검증한다.

RecordingSession
사용자·여행·시작/중지/종료·측정 시각과 상태. 수집 샘플의 유효 기록 구간 검증.
LocationSample / LocalOutbox
세션 ID·샘플 순번·좌표·정확도·측정 시각을 가진 전송 단위. 앱 Room에 미전송 보관; 서버 원시 위치 영구 보관은 미확정.
TripInvite
초대 토큰과 서버 발급/만료 시각. 유효기간 10분, 세부 재사용 정책은 미확정.

대상 날짜·변경 전후·생성 당시 plan_version·적용 상태. 버전이 오래되면 적용 거부·재계산. 저장 테이블 여부는 구현 시 결정.
RequestExecution
request_id 기반 중복 명령 방지와 성공 응답 재사용. 계획 변경과 일관된 커밋으로 관리하며 보관기간은 별도 결정.
RouteCache / ApiUsage
외부 경로와 만료 시각, 일별 호출 사용량의 관리 모델. 무료 한도·허용 이용기간 검증 후 구체화.
ImportJob
요청 소유자, 제공자·입력 출처, URL/게시물 ID, 상태·단계·만료·임대 토큰, 버전, 캡션 검증값과 후보 결과. 초기에는 관계형 작업 행 + 제한된 JSONB 결과 사용.
PlaceExternalRef (논리 모델)
공용 Place와 제공자·외부 장소 ID·검증 시점의 연결. 기존 source mapping이 있으면 재사용하며 물리 테이블 증설을 강제하지 않음.
ImportCandidate / Evidence (논리 모델)
원문 이름·주소·지역·Unicode 근거 구간·대조 결과·사용자 선택. 초기 ImportJob 결과 JSONB에 보관 가능하며 별도 업무 저장소로 분리하지 않음.

9.1 기본 요청 흐름
1.  Android 앱이 JWT를 포함해 Spring Boot REST API를 호출한다.
2.  Spring Boot 단일 서버가 PostgreSQL/PostGIS에서 데이터를 조회·수정한다. 계획 수정은 버전·요청 ID·트랜잭션을 적용하고 커밋 후 SSE를 전달한다.
3.  공공 관광/상가 데이터는 백엔드 수집 로직이 주기적으로 가져와 자체 DB에 정규화한다.
4.  사진 저장은 기존 로컬 스토리지 검토를 유지하며 추가 비용 없는 제공 방식을 우선한다. 외부 앱에는 인증·여행 권한을 확인하는 파일 API를 제공하고 서버 내부 경로를 노출하지 않는다.
5.  Android는 필요한 위치를 Room에 저장하고 묶어서 보낸다. 서버 H3가 CELL을 확정하며, Mapbox는 화면 범위·줌에 맞게 받은 CELL·마커·경로·썸네일을 표시한다.
로컬 파일 저장 시 주의
서버 PC 내부 파일 경로 자체는 외부 Android 사용자에게 보이지 않는다. 다중 사용자 테스트를 하려면 백엔드가 파일을 제공하는 HTTP 엔드포인트 또는 네트워크에서 접근 가능한 스토리지 구조가 필요하다.
외부 접속 시 주의
개발 단계에서 로컬 포트를 외부에 열어 사용할 수 있으나, 로그인/JWT/사진 업로드가 포함되므로 실제 외부 테스트에서는 TLS 적용이 가능한 리버스 프록시·터널 등 안전한 진입 경로를 고려한다.
9.2 비용 0원 운영 조건 및 외부 검증
이 절의 외부 서비스 확인 설명은 v1.2~v1.3 작성 당시 이력을 보존한 것이다. v1.4에서 기존 가격·모델·계정 조건을 모두 재검증한 것은 아니다. 현재 모델 ID·무료 범위·과금 차단은 연결 전 다시 확인한다.
Gemini: 이전 문서에는 사용자 지정 gemini-3.5-flash의 일반 Free Tier와 Search/Maps Grounding 구분을 확인했다고 기록되어 있었다. 이번 개정은 그 확인 결과를 재인증하지 않는다. 실제 지원 모델 ID와 무료 제공 여부를 공식 가격표·계정에서 확인하며, 모델 호출과 외부 검색 도구를 같은 무료 기능으로 가정하지 않는다. [E1]
운영 설계: Gemini Free Tier 프로젝트만 연결하고 유료 업그레이드·충전·유료 모델 폴백은 사용하지 않는다. 한도 부족 시 AI 사용 제한을 안내하되 자체 장소 검색과 여행 편집은 유지한다. 실제 프로젝트의 과금 상태와 한도는 AI Studio에서 확인해야 한다. [E2][E3]
AI 데이터 주의: 무료 서비스 약관은 제출한 입력/출력의 제품 개선 사용과 검토 가능성을 설명하고 개인정보·민감·기밀정보를 제출하지 말라고 안내한다. 따라서 원본 GPS, 개인 사진·메모, 실명과 식별자는 무료 AI에 보내지 않는 설계가 필요하다. [E4]
제안 구조: GPS 주변 검색·거리 계산·권한 검사는 STOG 서버에서 수행한다. Gemini에는 개인정보를 제외한 질문의 의도와 공개 장소 후보 등 필요한 최소 정보만 전달한다. 자유 입력도 개인정보 제거·차단을 거쳐야 하며, 무료 약관의 사용자 연령·지역 제한도 배포 전에 검토한다. [E4]
Mapbox: Android Maps SDK는 월간 활성 사용자(MAU) 기반이며 무료 범위와 초과 요금이 존재한다. 현재 선택은 유지하되 실제 계정의 과금 설정·무료 초과 차단을 검증하기 전에는 비용 0원을 보장한다고 적지 않는다. [E5]
비용 차단 조건을 만족하지 못하는 서비스는 연결을 보류한다. 길찾기·외부 검색·호스팅·사진 스토리지·배포도 별도로 검토하며, 유료 크레딧 구매나 카드 결제를 전제로 한 구성을 추가하지 않는다.
9.3 승인 기술과 호환성 확인
v1.3에서 채택한 화면·통신·DB·H3 구성을 유지한다. v1.4에는 Instagram 추출 보조 Node.js/Playwright 프로세스를 추가한다. Java/XML 앱과 Spring Boot 주 서버를 바꾸지 않으며 라이브러리·브라우저·환경 버전은 구현 전 고정·검증한다.
Java로 호출 가능한 라이브러리와 라이브러리 내부 구현 언어는 구분한다. OkHttp의 Kotlin 런타임 의존성은 과제의 “Kotlin 금지”가 앱 소스만을 뜻하는지 확인한 후 적용한다. 허용 범위가 다르면 조용히 위반하지 않고 해당 통신 라이브러리 선택을 재검토한다. [E23]
초기 채택 제외: Redis, Kafka, Elasticsearch, 별도 벡터 DB, 마이크로서비스, Kubernetes. 병목이나 운영 요구가 실측으로 확인되기 전 추가하지 않는다.
9.4 단일 서버 운영과 지연 분리
Spring MVC 주 애플리케이션 한 개와 PostgreSQL 한 개를 기본으로 한다. Instagram 브라우저 추출만 같은 기존 서버 환경의 제한된 보조 프로세스로 분리한다. 별도 유료 호스팅·서비스별 DB·마이크로서비스 재구성을 의미하지 않는다.
일반 조회·수정은 화면에 필요한 필드·개수만 반환한다. 공간 조회와 버전 조건부 갱신에는 명시적인 SQL을 쓰되, 같은 작업에 서로 다른 버전 증가 규칙을 중복 적용하지 않는다.
AI·길찾기·사진·Instagram 브라우저 처리처럼 느린 작업을 기다리는 동안 DB 트랜잭션을 유지하지 않는다. 일반 여행 편집과 실행 슬롯·대기열을 분리하고 각각 상한을 둔다. 정확한 상한은 서버 사양에 맞춰 측정한다.
외부 API 한도와 파일·썸네일 캐시에는 상한·만료를 둔다. 무료 한도를 벗어나면 해당 외부 기능만 제한하며 기본 여행 편집·검색·기록을 유료 서비스로 전환하지 않는다.
9.5 Android 상태·통신·작업 관리
HTTP 클라이언트는 화면마다 새로 만들지 않고 재사용한다. 검색은 필요 없는 요청을 취소하거나 오래된 응답을 무시하고, 뒤로 가기 시 기존 검색어·결과·스크롤 위치를 복원한다. [E22][E23][E24]
ViewModel은 화면 상태, Repository는 데이터 접근, Room은 필요한 로컬 데이터·전송 대기열을 담당한다. Fragment의 화면 코드에 위치 수집·통신·상태를 모두 넣지 않는다.
위치 기록은 Foreground Service, 재시도는 WorkManager, 렌더링은 보이는 지도 화면으로 책임을 나눈다. 전송 큐의 성공 확인과 중복 방지를 함께 검증한다. [E7][E17]
9.6 성능 검증과 조정 기준
서버 사양, 데이터량, 동시 사용자 수가 아직 정해지지 않았으므로 성능 수치는 초기 시험 목표다. P95는 측정 요청의 95%가 그 시간 안에 처리되는 지점이며 평균과 함께 기록한다.
시험
측정·검수 내용
지도 확대·이동
CELL·사진 수를 단계적으로 늘려 프레임 지연, 메모리, 서버 응답 크기, 이미지 요청 수 확인.
정지·보행·화면 잠금
정지 중 오활성화, 실제 보행 누락, 경계 흔들림, 화면 꺼짐 이후 배터리·기록 유지 측정.
동시 편집·재시도
같은 버전의 수정 두 개가 조용히 덮어써지지 않는지, 응답 유실 후 재시도가 중복 저장되지 않는지 확인.
DB 조회·수정
검색·주변 조회·계획 수정의 평균·P95, 쿼리 수, 실행 계획과 인덱스 사용을 확인. [E27]
Instagram 추출·확인
캡션 확보·후보 추출·Place 대조·사용자 확인을 분리 측정한다. 대기시간·브라우저 메모리·단계별 지연·오연결·부분 결과·수정률을 기록하며 성공 두 건을 운영 성능으로 사용하지 않음.
초기 목표: 외부 API 대기가 없는 일반 서버 조회·수정의 P95 300ms 이내를 시험 출발점으로 삼는다. 보장값·실측 결과가 아니다. GPS 대기·배치·길찾기·AI·Instagram 브라우저 추출·사용자 확인·단말 렌더링은 별도 측정하며, 202 작업 접수와 완료 지연을 혼동하지 않는다.
조정 순서: 보이지 않는 데이터·사진 요청 감소 → 중복 요청·과도한 재조회 감소 → 실제 DB 쿼리와 인덱스 조정 → 실행 동시성·큐 상한 조정 → 필요성이 입증된 경우에만 추가 캐시·서버 도입.

12.1 여행 기간 단축 처리 제안 — 미승인
제안: 새 기간 밖의 일정 장소를 보여 주고, 사용자 확인 후 여행 바구니로 돌려보낸다. 날짜를 바꾸는 것만으로 기존 사진·CELL 방문 기록은 삭제하지 않는다. 원래 순서 보존과 같은 장소 중복 처리는 함께 정해야 한다. 이 문구는 사용자 승인 전 확정 정책이 아니다.
13. 핵심 완료 조건
프로젝트의 핵심 가치를 증명하기 위해 최소한 아래 시나리오가 끊기지 않고 동작해야 한다.
두 사용자가 하나의 여행에 참여해 같은 바구니와 날짜별 일정을 수정하고 결과를 공유할 수 있다.
Instagram 게시물 링크를 공유/붙여넣기로 받아 캡션·후보·실제 장소를 단계별로 확인하고, 사용자가 선택한 장소만 진행중/예정 여행 바구니에 저장할 수 있다. 카카오·네이버 링크는 후속 완료 조건으로 분리한다.
바구니 장소가 선택 날짜 일정으로 이동하면 바구니에서 제거되고, 순서 변경 시 지도 번호·동선도 함께 바뀐다.
촬영 사진·위치를 기기에 보관하고 서버 동기화가 완료되면 해당 CELL을 활성화한다. 오프라인 대기·업로드 재시도 상태를 실제 확정 집계와 구분한다.
같은 CELL에 여러 기록이 있으면 열람 가능한 최신 사진이 대표로 보이며, 상세 시트에서 최신순으로 확인한다.
공개 선택 사진만 발견에 나타난다. 여행 비공개 사진은 해당 여행 구성원이 볼 수 있고, 비구성원과 공개 지도에는 노출되지 않는다.
발견 또는 STOBEE에서 찾은 장소를 다시 여행 바구니로 저장할 수 있다.
홈 여행 카드에서는 계획 편집 화면이 아니라 지도 중심 실행 화면으로 진입한다.
홈의 자체 검색에서 찾은 장소를 STOBEE 지도에서 확인하고 여행 바구니에 저장할 수 있으며, 필요할 때만 AI 채팅으로 전환된다.
사용자가 시작한 여행 기록 세션은 화면이 꺼져도 유효 샘플을 수집한다. 중지·종료 뒤 측정된 위치는 제외하고, 그 전에 수집한 미전송 데이터는 중복 없이 동기화한다.
STOBEE의 나의 지도 ON/OFF와 줌 변경은 표시만 바꾸며 CELL 수·경험치·기록 세션 상태를 변경하지 않는다.
장소 상세·채팅 시트가 열려 있어도 노출된 지도를 움직일 수 있고, 두 시트를 겹쳐 표시하지 않는다.
여러 장소 게시물에서 사용자가 선택한 장소만 바구니에 저장되고, 공유 사진 전체가 자동 저장되지 않는다.
초대 링크는 10분 후 신규 참여를 거부하고, 관리자는 나가기가 불가능하며 일반 구성원은 여행 삭제가 불가능하다.
동선 변경안은 적용 전까지 원본에 영향을 주지 않는다. 적용 시 계획 버전을 검사하고, 저장 성공·커밋 뒤 SSE로 다른 구성원에게 변경을 알린다.
현재 GPS 주변 요청은 지도 중심과 무관하게 GPS를 기준으로 하며, Gemini 무료 한도 부족 시 유료로 전환하지 않는다.
같은 사용자·CELL의 반복 전송과 사진 추가가 CELL 수·최초 활성화 경험치를 중복 증가시키지 않는다.
같은 plan_version으로 동시에 보낸 수정은 조용히 덮어써지지 않고 충돌이 안내된다. 실패한 이동은 기존 항목을 보존한다.
같은 request_id의 재전송은 중복 생성·이동을 만들지 않는다. SSE 유실·재연결 이후 REST 재조회로 최신 상태를 복구한다.
지도는 현재 범위·줌에 필요한 도형·썸네일만 요청하며, 화면 꺼짐 상태에서 불필요한 지도·방향 렌더링을 계속하지 않는다.
무료 길찾기 한도 도달·응답 실패 시 해당 기능만 제한하며, 만료 경로를 재사용하거나 직선을 실제 길찾기로 표시하지 않는다.
일반 조회·수정과 GPS 대기·배치 지연·외부 API 지연을 따로 측정하고, 9.6절의 성능 목표를 실제 시험 결과와 구분해 기록한다.
13.1 Instagram 1차 완료 조건
원문 자동 수집의 실패와 후보 없음·실제 장소 미해결을 구분한다. 부분 결과를 모두 성공 또는 모두 실패로 뭉치지 않는다.
백엔드에서 수집·파싱·대조하며 앱은 공유 수신·진행·근거·선택을 담당한다. Instagram 사용 시 LLM·유료 fallback·개인 브라우저 쿠키 사용이 기본 경로에 없어야 한다.
사용자 확인 전 Place의 추정 주소·좌표를 확정하지 않는다. 미해결 장소가 현재 GPS로 매칭되거나 CELL·EXP·발견 Post를 만들지 않아야 한다.
작업 조회 권한, URL/SSRF 방어, 제한시간·동시성·임대 만료, 장애 복구, 버전·중복 요청을 시험한다. 상세 테스트는 14.13절을 따른다.
로컬 보고 두 URL과 별도 형식 표본을 구분해 평가하며 실패·미검증도 남긴다. 보고된 두 건의 캡션 성공을 전체 장소 매칭 또는 서버 안정성으로 확대하지 않는다.
13.2 카카오·네이버 후속 완료 조건
각 제공자의 실제 공유 링크를 검증해 동일한 공통 Place 대조·사용자 선택·여행 바구니 흐름으로 연결한다. Instagram용 Playwright를 지도 링크에도 무조건 적용하지 않는다. 후속 단계 이전에는 UI에서 지원 완료로 표시하지 않는다.
STOG의 핵심
“여행을 함께 계획한다”와 “내가 실제로 걸어간 흔적을 지도에 채운다”가 하나의 흐름 안에서 연결되는 것이 프로젝트의 가장 중요한 정체성이다.
14. Instagram 우선 구현 상세 명세
문서 상태: 구현할 설계. 두 게시물 로컬 검증은 부록 D의 사용자 제공 보고서에 근거한다. 이번 문서 편집에서 대상 게시물·스크립트·결과 JSON을 재실행하거나 앱·서버를 구현하지 않았다. 기술적 접근 가능성의 근거를 확보했다는 사용자 판단에 따라 구현 순위를 올리되, 서비스 안정성·모든 형식 지원·이용 허용을 검증 완료로 바꾸지 않는다.

Android Java/XML 앱은 URL 공유·붙여넣기·진행·후보 확인·저장. 수집·파싱·Place 대조·API 키는 백엔드 담당.
재사용
Spring Boot + PostgreSQL + 기존 Place·TripItem·공통 검색·지도 상세·REST/SSE·버전·중복 요청 방지. SQLite·새 개인 저장목록·InstagramPlace 서버를 추가하지 않는다.
새 구성
Node.js + Playwright 추출 보조 프로세스와 PostgreSQL의 ImportJob. 별도 유료 호스팅·Redis/Kafka·벡터 DB는 초기 제외.
LLM 기본안
캡션 확보에는 LLM을 사용하지 않는다. 장소 후보 추출은 규칙을 기본으로 하며 instagram.caption_llm_enabled=false로 시작한다. 비교 검증 전 자동 LLM fallback 없음.
제외 범위
댓글 수집, 사진 OCR, 영상 음성 인식, 영상/원본 사진 다운로드·재게시, 로그인/CAPTCHA 우회, 개인 쿠키 재사용, 직접 일정·CELL 자동 생성은 이번 범위 아님.
형식 상태
/p/ 두 URL의 캡션·규칙 파싱만 보고됨. /reel/과 다른 레이아웃은 별도 검증 목록이며 기존 성공으로 간주하지 않는다.
이 절은 범용 보고서의 STOG 적용 규칙이다. 부록 D의 플랫폼·DB 미결정 문구를 근거로 Java/XML·Spring Boot·PostgreSQL을 재선정하지 않는다. 카카오 로컬 “검색 API” 후보는 카카오 지도 “공유 링크”의 개발 우선순위와 구분한다.
14.2 사용자 흐름과 Android 연결
Instagram 공유/링크 붙여넣기 → 인증·입력 확인 → 202 작업 접수 → 캡션 확보 → 후보 분리 → Place 대조 → 사용자가 장소 확인 → 대상 여행 선택 → 바구니 저장. 추출은 여행 계획의 변경이 아니며 최종 저장 직전에만 계획 권한·버전을 확인한다.
Android의 ACTION_SEND + text/plain 및 EXTRA_TEXT를 처리하는 공유 수신 Activity/기존 라우팅을 사용한다. 외부 입력을 검사하고 onCreate/onNewIntent 경로에서 중복 접수를 방지한다. Java/XML을 유지하며 공식 공유 안내의 Compose 예제로 앱을 전환하지 않는다. [E28]
공유 텍스트에 URL 외 문장이 있어도 원문을 보존하고 허용 URL만 분리한다. URL이 여러 개면 하나를 사용자에게 선택받으며 일괄 크롤링하지 않는다. Instagram 도메인의 App Links 소유권을 STOG가 주장하거나 URI를 검증된 딥링크로 취급하지 않는다.
여행 바구니에서 진입한 경우 trip_id를 입력 문맥으로 보존한다. 외부 앱에서 바로 진입하면 저장 시 여행을 고른다. 후보를 지도로 확인할 때는 공통 장소 상세를 이용하고 결과 페이지의 작업 ID·근거·선택 상태를 복원한다. 링크 공유만으로 캡션·정확한 좌표가 전달된다고 가정하지 않는다.
실패 보조: 사용자가 직접 캡션을 붙여넣을 수 있게 한다. input_type=USER_TEXT, caption_source=user_input으로 별도 접수하여 같은 규칙 파서·Place 대조를 사용한다. 기존 자동 수집 실패는 성공으로 덮어쓰지 않고 수동 입력 결과의 출처도 URL 자동 검증과 분리한다.

Node.js는 기존 검증 코드 재사용을 위한 추출 전용 보조 프로세스다. Spring Boot 전체를 Node.js로 바꾸지 않는다. 초기에는 기존 서버의 제한된 내부 통신으로 호출하고 추출기를 인터넷에 직접 공개하지 않는다. 사용자 JWT·DB 자격증명·외부 장소 API 키를 브라우저 페이지에 전달하지 않는다.
같은 유효 캡션에 규칙을 다시 적용하는 작업은 새 브라우저 수집과 분리한다. 결과 재사용 가능 기간·원문 보관은 제공자 조건과 14.11절을 따른다. 캐시 적중을 실제 새 수집 성공으로 집계하지 않는다.
14.4 비동기 작업·상태 계약
초기 저장은 PostgreSQL ImportJob 행 하나와 크기를 제한한 결과 JSONB로 시작한다. 목록·권한·임대·정리용 키는 일반 컬럼으로 둔다. 작업 상태, 처리 단계, 후보별 연결 상태, 여행 저장 결과를 하나의 status에 섞지 않는다.
상태 축
값 예시
해석
job_status
QUEUED / RUNNING / COMPLETED / FAILED / EXPIRED
수집·추출·대조 파이프라인의 실행 상태. COMPLETED는 저장 완료가 아님.
stage
VALIDATING / FETCHING / PARSING / MATCHING / READY
현재 단계. 완료 전 정확한 진행 백분율을 임의 생성하지 않음.
candidate_status
MATCHED / NEEDS_CONFIRMATION / UNRESOLVED
후보별 Place 연결 상태. MATCHED여도 바구니 저장 전 사용자 확인 필요.
outcome
RESULTS / PARTIAL / NO_CANDIDATES
작업이 끝난 후 결과 성격. NO_CANDIDATES는 파서가 못 찾았다는 뜻이며 게시물에 장소가 없다고 증명하지 않음.
오류 코드
FETCH_FAILED / ACCESS_RESTRICTED / CAPTION_NOT_FOUND / CAPTION_MISMATCH / TARGET_MISMATCH / TIMEOUT
실패 원인. HTTP 200 또는 브라우저 document 응답만으로 성공 판정하지 않음.
검증 정보
caption_complete=true / false / null
같은 게시물의 JSON과 정규화 일치 / 비교 불일치 / 비교 불가. 독립된 원저자 원본 검증이 아님.
원문 보고서의 no_places는 이 계약에서는 NO_CANDIDATES에 대응하는 파서 결과로 취급한다. 세 후보 중 두 개만 연결되면 작업은 COMPLETED + PARTIAL일 수 있고 세 후보 각각의 상태를 유지한다. 후보 수 0도 자동 수집 실패와 다른 결과로 응답한다.
처리기는 짧은 트랜잭션에서 QUEUED를 선점하고 임대 토큰·기한을 기록한 뒤 트랜잭션을 닫는다. 브라우저·외부 API 완료 후 유효한 임대 토큰에 대해서만 결과를 저장한다. 프로세스 중단으로 임대가 만료된 작업은 제한된 횟수만 재시도하거나 실패 처리한다. 이전 실행의 늦은 응답이 새 결과를 덮어쓰지 않아야 한다.
14.5 캡션 확보·무결성·근거 보존
기본 확보 경로는 보고서에서 검증된 Playwright DOM locator.innerText()다. [E30] 일반 HTTP를 먼저 반복하는 단계는 이번 시험에서 이득이 확인되지 않아 필수로 넣지 않는다. 페이지 script JSON은 같은 게시물과 연결되는 경우 비교 근거로 사용하며 별도 공개 API라고 부르지 않는다.
검사
처리 기준
대상 식별
정규화한 게시물 종류·shortcode와 최종 URL·페이지 대상이 일치하는지 확인한다. 다른 추천 게시물 캡션을 대신 반환하지 않는다.
DOM 수
해당 게시물에 속한 유일한 캡션 요소인지 확인. 0개·여러 개를 성공으로 처리하지 않는다. 원문 코드의 CSS 선택자는 미제공이므로 임의로 검증된 선택자를 만들어 적지 않는다.
JSON 비교
대상 게시물 ID와 연결된 JSON에만 대조한다. 동일 공백·줄바꿈 정규화 후 같으면 true, 다르면 false, 비교 기준이 없으면 null.
false 처리
CAPTION_MISMATCH로 검증 실패를 알리고 해당 결과로 자동 장소 확정을 진행하지 않는다. 사용자 본문 입력은 별도 출처의 새 결과로 처리.
null 처리
비교 미확인 표시와 함께 확보한 원문 범위만 후보 추출 가능. 전체 캡션 보장으로 표시하지 않고 사용자 확인을 강화.
원문·정규화
caption_raw를 유지하고 검색용 정규화·별칭과 분리한다. 원문 이름·주소·지역·근거를 외부 지도 데이터로 덮어쓰지 않는다.
근거는 원문 문자열의 실제 연속 구간을 사용한다. 여러 줄을 함께 근거로 삼으면 여러 evidence_spans를 보관하고 존재하지 않는 단일 인용문을 합성하지 않는다. 공통 오프셋 규약은 Unicode code point 기준 [start,end)로 두고 JS/Java 구현에서 변환·검증한다. 원문 변경·정규화 후 오프셋을 그대로 재사용하지 않는다.
API·스키마에 raw 문자열 길이, 후보 수·근거 구간 수의 상한을 두고 초과 시 제한 상태로 처리한다. silent truncation 후 caption_complete=true로 보고하지 않는다. 웹 페이지 텍스트를 명령으로 실행하거나 HTML로 신뢰 렌더링하지 않는다.
14.6 비LLM 후보 추출과 실제 장소 대조
캡션 확보, 후보 파싱, Place 식별은 독립 단계다. 기존 두 표본의 번호·핀·주소 규칙은 회귀 테스트로 보존하되 그 형식에만 맞춘 파서를 범용 한국어 장소 추출기로 표시하지 않는다.
순서
채택 처리
1. 원문 구간화
줄·번호·핀 표기와 주소 후보를 단서로 구간을 만든다. 문장·줄 위치를 보존하고 번호가 없으면 무조건 장소로 분리하지 않는다.
2. 필드 분리
구간 안 이름·도로명/지번 주소 후보·지역·지점명을 분리한다. 주소가 없으면 address_raw=null 유지. 현재 위치나 추정 주소로 채우지 않는다.
3. 관계 확인
이름-주소의 같은 구간·줄 인접성·번호 경계를 검사한다. 두 가게와 주소가 얽히면 후보를 확인 필요로 남기고 잘못 짝짓지 않는다.
4. 자체 DB 후보
기존 Place의 정규화 이름·별칭·지역·지점·주소를 조회한다. 게시물의 지역 근거를 우선하며 현재 GPS를 기본 필터로 쓰지 않는다.
5. 제한 외부 보완
DB에 없거나 후보가 모호할 때만 승인된 무료 키워드 장소 검색을 호출한다. 연결 불가·한도 부족 시 사용자 검색/미해결로 남긴다.
6. 사용자 확인
이름만 같은 첫 결과를 확정하지 않는다. 주소·지역·지점·출처·확인 시각과 원문 근거를 제시하고 사용자가 저장할 Place를 선택한다.
명확한 단일 대조 결과는 MATCHED, 복수 지점·불충분 근거는 NEEDS_CONFIRMATION, 실제 장소를 찾지 못하면 UNRESOLVED로 반환한다. 정규화 유사도 점수를 검증된 확률처럼 표시하지 않는다. 주소만 geocoding한 결과와 업소의 Place 식별은 별개다. [E31]
미해결 후보의 수동 보완은 기존 장소 검색에서 실제 Place를 확인하는 경로다. 사용자가 이름을 수정하면 user_override를 별도로 남기고 원문 추출 결과·공용 Place를 즉시 수정하지 않는다. 외부 검색으로 얻은 Place를 내부에 영속화할 수 있는지는 제공자 조건을 확인한 뒤 처리한다.
예시: 제공된 보고서의 덕진공원 후보 (실제 장소 매칭 전){  "name_raw": "덕진공원",  "address_raw": null,  "region_raw": "전주",  "evidence": "📍전주 덕진공원 일원",  "place_id": null,  "candidate_status": "NEEDS_CONFIRMATION"}
14.7 LLM 사용 여부의 판단과 검증 조건
현재 채택 판단: 캡션 수집은 비LLM, 후보 구조화도 규칙 기반을 기본으로 구현한다. 명시적인 이름·주소 형식에서 이미 규칙 추출이 보고되었고, 추가 모델 호출·모델 출력 검증·외부 전송·무료 한도 의존성을 기본 경로에서 제거할 수 있기 때문이다. 이는 구성상 판단이며 두 URL로 전체 정확도·총 지연시간의 우열을 실측한 결론은 아니다.

비교 설계: 같은 확보 캡션과 같은 Place 후보 DB를 사용하여 A=규칙+사용자 확인, B=규칙+어려운 캡션에 한정한 LLM 보조를 비교한다. 두 회귀 URL과 별도의 평가 표본을 분리하고, 캡션 확보 지연과 후보 파싱 지연을 분리한다. 비교를 위해 매번 Instagram 브라우저 접근을 반복할 필요는 없다. 아직 B 실험이나 모델 호출을 수행하지 않았다.
측정 항목
판단에 필요한 이유
후보 precision / recall
추출한 장소의 정답 비율과 원문 장소의 누락 비율을 분리. 형식별로 보고한다.
이름-주소 연결 / Place 오연결
후보 추출 개선이 잘못된 지점·주소 연결 증가로 상쇄되지 않는지 확인.
사용자 수정·확인 부담
자동 처리시간만 아니라 사람이 고치거나 검색하는 횟수·시간도 포함.
단계별 p50·p95·메모리
브라우저, 파서, DB, 외부 API, 선택적 LLM을 구분. 캐시·서버 환경을 기록.
실제 비용·외부 전송·운영
무료 한도·모델 장애·데이터 전송·출력 검사·의존성 부담이 추가되는지 확인.
LLM을 켜는 조건은 규칙 기준선으로 해결하기 어려운 오류가 독립 표본에서 확인되고, B가 사용자 수정 부담/누락을 의미 있게 줄이면서 오연결·개인정보·비용 0원·응답 예산을 위반하지 않는 경우로 제한한다. 목표 수치는 측정 전에 명시하고 사후에 결과에 맞춰 바꾸지 않는다. 실익이 불분명하면 계속 비LLM으로 운영한다.
나중에 LLM을 시험하더라도 외부 텍스트를 도구 명령으로 취급하지 않고 구조화된 후보만 받는다. JSON 스키마·근거 구간·게시물 ID·필드 타입을 검증하고, 근거가 존재해도 이름-주소 관계는 별도 대조한다. 유료 모델 전환·자동 재호출·개인 GPS/비공개 사진 전송은 허용하지 않는다.
14.8 REST 계약 초안과 저장 원자성
아래 경로·필드명은 이번 구현에 사용할 계약 초안이다. 기존 코드의 경로가 다르면 의미를 유지해 통일한다. 새 개인 저장 서비스나 사용자별 Instagram 데이터베이스를 만들지 않는다.

{  "trip_id": "&lt;target-trip-id&gt;",  "result_version": 1,  "expected_plan_version": 12,  "request_id": "&lt;new-request-uuid&gt;",  "selections": [    {"candidate_id": "c1", "place_id": "&lt;verified-place-id&gt;"}  ]}
확인 요청의 candidate_id·place_id는 서버의 후보 결과나 사용자가 수행한 검증된 장소 검색 선택과 대조한다. 외부 응답의 ID와 내부 place_id를 혼동하지 않는다. 임의의 좌표·공용 Place 수정값을 그대로 신뢰하지 않는다.
초기 확인 저장은 사용자가 선택한 유효 항목 묶음을 한 트랜잭션에서 전부 저장하거나 전부 취소하는 방식이다. 미해결 항목이 섞였으면 저장 가능한 부분집합을 사용자가 다시 선택하도록 안내한다. 추출의 부분 성공과 저장의 원자성은 다른 정책이다.
권한과 request_id 재시도 결과를 먼저 확인한 뒤 신규 명령에는 plan_version을 검사한다. 같은 소유자·명령 종류·request_id와 같은 입력이면 이미 커밋한 결과를 재응답한다. 같은 키의 다른 입력은 충돌로 거부한다. 재시도에 오래된 expected_version이 포함되어도 이미 성공한 동일 명령을 다시 실행하지 않는다.
새 저장 요청의 결과 버전 또는 여행 계획 버전이 바뀌면 409와 최신 확인 필요를 안내하고 재조회한다. 사용자 선택을 조용히 다른 Place로 변경하지 않는다. 사용자 탈퇴·여행 삭제·종료 상태 변경 등은 최종 저장 시 재검사하며 성공 커밋 후에만 여행 SSE를 보낸다.

14.10 지연·메모리·처리량 관리
다음 수치는 측정 전 구현 시작값이다. 작업 처리 완료나 외부 사이트 응답에 대한 보장값이 아니며 환경·부하 시험 후 조정한다. 일반 여행 요청의 P95 목표와 브라우저 추출 지연을 섞지 않는다.
제어
초기값·방향
브라우저 동시 실행
작업 1개부터 시작. 한 worker가 browser를 재사용하되 작업마다 새 비영구 context를 만들고 종료 시 정리. [E29]
접수 상한
사용자별 진행 작업 1개, 전체 대기 20개부터 검증. 초과 시 접수 제한과 재시도 안내; 무제한 대기열 금지.
전체 실행 제한
실행 시작 후 45초부터 시험; 큐 대기시간과 분리. DOM 대기만 아니라 fetch·parse·match 전체에 예산을 배분.
재시도
일시적 네트워크/프로세스 오류에만 총 2회 이하 시도부터 검증. CAPTCHA·로그인 요구·미지원·명확한 캡션 없음은 자동 반복하지 않음.
앱 상태 조회
표시 중 약 2초에서 시작해 최대 5초 간격으로 완화. 완료·실패·화면 이탈 시 중단, 복귀 시 한 번 재조회.
브라우저 리소스
필요 없는 이미지·동영상·진단 본문을 상시 저장하지 않는다. 요청 차단은 추출 정상 동작을 먼저 비교 검증하고 필수 document/script까지 무작정 차단하지 않음. [E33]
메모리·작업 정리
browser+자식 프로세스 RSS·처리 수·오류를 측정해 상한 초과 시 정리/재시작. 숫자는 서버 사양 측정 후 결정.
처리 중 job lease·오류·최종 시각을 남겨 장애 후 영구 RUNNING을 방지한다. Playwright 타임아웃만으로 Spring·외부 API·프로세스 자원이 모두 회수되는 것으로 간주하지 않는다. stale worker 응답 차단과 context 정리를 별도 시험한다.
규칙 파싱은 유효 캡션 한 번에 수행하고 정규화 결과·후보를 재사용한다. 후보마다 여러 외부 API를 무한 조합하지 않고 DB 우선, 제한된 후보 검색, 무료 호출 상한을 적용한다. 원문 네트워크 fetch/XHR 전체를 메모리에 모으는 진단 방식은 기본 비활성화한다.
14.11 보안·비용·보관·외부 조건
URL 검사는 HTTPS·정확한 호스트 허용목록·허용 경로/shortcode·포트를 파서로 확인한다. 자격정보가 포함된 URL·다른 스킴·임의 URL은 거부하고, 검증된 provider/type/shortcode에서 수집 URL을 서버가 재구성한다. Java와 Node의 파서 해석 차이가 있으면 허용 쪽으로 맞추지 말고 거부한다. [E32]
리디렉션과 브라우저 하위 요청도 대상 제한을 적용하고, IPv4/IPv6 내부망·루프백·링크로컬·메타데이터 주소 접근은 네트워크 계층에서 차단한다. BrowserContext는 세션 데이터 격리이며 SSRF·서버 권한 격리를 대체하지 않는다. worker 제어 채널과 브라우저 외부 접근은 분리한다. [E29][E32]
개인 Chrome 프로필·쿠키·로그인 세션을 복사하지 않는다. 로그인/CAPTCHA/접근 제한은 명시적 실패로 처리하고 우회하지 않는다. 플랫폼의 자동 수집·재사용 허용은 별도 출시 점검 사항이며 기술적 HTTP/DOM 성공과 구분한다. Meta의 공식 설명은 자동 수집과 이용 허가를 구분하지만, 현재 Instagram 세부 약관에 대한 적합성 판정은 이번 문서에서 완료하지 않는다. [E34]
프로젝트의 추가 비용 0원은 Instagram에도 적용한다. 유료 스크래핑 서비스·프록시·외부 LLM·자동 모델 fallback을 넣지 않는다. 무료 외부 장소 API를 쓸 수 없으면 자체 DB와 사용자 확인으로 범위를 제한하고 오류를 명확히 안내한다. 브라우저 작업의 CPU·메모리·기존 PC 운영 부담이 없다는 뜻은 아니다.
원문·근거·수집 결과·외부 응답별 보관 범위와 기간을 제공자 조건에 따라 정한다. 기간이 확정되지 않으면 운영에서 무기한 캡션/응답 캐시를 켜지 않는다. 삭제·수정·폐업 가능성을 고려해 수집·확인 시각과 버전을 보관하고 만료 시 재확인한다. 전체 캡션을 공용 로그에 남기지 않는다.
수집 캡션은 공개 여부와 무관하게 신뢰할 수 없는 입력이다. 길이·후보 수·JSON 스키마를 검증하고, API 키·JWT·내부 경로·원문 개인정보를 일반 로그에 기록하지 않는다. caption_source=user_input은 다른 사용자의 같은 URL 작업과 자동 공유하지 않는다.

IG-06의 규칙 실패 유형을 근거로만 별도 비교. 실익 없거나 무료/데이터 조건 불충족이면 OFF 유지.
IG-08
카카오·네이버 후속
공통 저장을 재사용하여 지도 링크별 어댑터 구현. Instagram 완료와 별도 지원 상태 관리.
평가 표본은 단일/복수 장소, 주소 없음, 번호 없는 나열, 지번주소·층/호·지점명, 짧은 캡션, 릴스, 이미지에만 주소, 삭제·비공개·로그인 요구·DOM 변경 등을 포함한다. 이미지에만 주소가 있으면 캡션 범위로는 추출하지 못할 수 있음을 정상 제한으로 기록한다. 댓글·OCR·음성 기능을 자동 추가하지 않는다.
측정은 URL 접수 수, 접근/캡션 확보 수, 비교 가능한 캡션 수, 실제 추출 후보 정답·누락, Place 오연결, 사용자 확인/수정, 작업 실패·부분 결과를 각각 분모와 함께 보고한다. 두 회귀 표본을 전체 평가와 합쳐 범용 성공률을 부풀리지 않는다. 목표 수치·데이터셋은 구현 전 정하고 아직 달성값을 기재하지 않는다.
14.14 AI 구현 시 금지할 추정과 완료 보고 규칙
문서의 Node.js 검증 기록을 근거로 존재하지 않는 운영 코드·CSS 선택자·JSON 결과·실행 로그를 만들어내지 않는다. 실제 파일이 없으면 원문 스크립트 제공 또는 구현 작업을 별도로 요구한다.
Instagram 공유 텍스트를 받았다는 이유만으로 캡션·Place ID·좌표를 얻었다고 보고하지 않는다. 각 단계가 실제로 수행된 경우에만 완료로 표시한다.
카카오·네이버 공유를 다시 1순위로 되돌리지 않는다. 외부 Place 보완용 카카오 API 검토와 링크 지원 순서를 혼동하지 않는다.
STOBEE 모델 계획을 근거로 Instagram에 LLM을 자동 연결하지 않는다. 후보 파싱의 LLM 보조 기본 OFF와 별도 비교 기준을 유지한다.
단일 Spring Boot·PostgreSQL·비용 0원·기존 Java/XML을 유지한다. 보고서 원문의 SQLite 대안이나 플랫폼 미결정을 그대로 적용하지 않는다.
공용 Place·TripItem·지도·협업 저장을 재사용한다. 새 Instagram 피드·개인 보관함·외부 사진 재게시·검색 기반 CELL 활성화를 만들지 않는다.
기존 미확정인 여행 기간 단축·초대 재사용·경험치 밸런스·무료 길찾기 조건을 이번 Instagram 변경으로 자동 승인된 것으로 처리하지 않는다.
완료 보고는 수정된 파일·코드·마이그레이션·실행한 시험·실패/미실행을 나누어 남긴다. 명세 작성과 실제 서비스 구현·배포를 분리한다.

4. 앱과 백엔드 처리 방식 제안
역할과 작업 흐름
앱의 URL 전달 → 백엔드 작업 접수 → 캡션 확보 → 장소 후보 분리 → 자체 DB 대조 → 필요 시 외부 검색 → 앱에서 확인·저장
앱은 링크 공유 수신 또는 붙여넣기, 상태 표시, 결과 선택·수정·저장을 담당한다. 앱 플랫폼별 공유 수신 구현은 아직 정하지 않았다. Playwright, Instagram 수집, 외부 API 키 관리, 장소 매칭은 백엔드에서 처리한다.
브라우저 작업은 지연·실패 가능성이 있으므로 비동기 처리를 제안한다.
1. 앱이 URL을 보내면 백엔드가 인증·URL 검사 후 job_id를 반환한다.
2. 백그라운드 처리기가 캡션 추출과 장소 대조를 수행한다.
3. 앱은 작업 상태를 조회하고 결과를 표시한다.
4. 사용자가 확인한 장소를 사용자 저장 목록에 연결한다.
초기에는 DB 작업 테이블과 처리 프로세스 하나로 시작한다. 작업에는 소유 사용자, 상태, 시작 시각, 만료 시각, 제한된 재시도 횟수를 둔다. 처리 중 장애가 나면 영구히 멈추지 않도록 만료 작업을 실패 처리하거나 재접수한다. 별도 메시지 큐는 실제 처리량과 운영 요구가 생길 때 도입한다.
캡션 확보
현재 검증된 Playwright DOM 추출을 기본 경로로 사용한다. 일반 HTTP 선행 요청은 이번 시험에서 이득을 확인하지 못했으므로 초기 필수 단계로 넣지 않는다.
게시물 ID와 최종 URL이 요청한 대상인지 확인한다.
작업별 브라우저 컨텍스트를 분리하고 종료 시 정리한다.
DOM 후보가 0개이거나 여러 개면 성공으로 처리하지 않는다.
JSON 대조 시 해당 게시물 ID와 연결된 캡션인지 먼저 확인한다.
JSON 대조가 불가능하면 완전성은 null, 대조 결과 불일치이면 false로 구분한다.
수집 실패 시 사용자 본문 붙여넣기를 보조 경로로 제공할 수 있다. 이때 출처는 user_input으로 기록하며 URL 자동 수집 성공에 포함하지 않는다.
장소 후보 추출
캡션의 원문 이름·주소·지역·근거 구간을 보존하고, DB 검색용 정규화 값은 별도로 만든다. 현재 규칙은 두 자리 번호, 📍, 일부 도로명주소 패턴과 전주 위치 문구에 맞춰져 있다. 일반적인 한국어 장소 추출기로 간주하면 안 된다.
LLM은 규칙으로 처리하기 어려운 게시물에 선택적으로 적용한다. JSON 형식·필드 타입을 검증하고, 근거 문장 또는 문자 구간이 실제 캡션에 존재하는지 검사한다. 캡션은 명령이 아닌 외부 데이터로 취급하고 도구 실행 권한을 주지 않는다. 근거 문자열 존재만으로 장소·주소 연결의 정확성까지 보장되지는 않으므로 별도 대조가 필요하다.

일부 장소만 연결 성공
장소별 상태와 함께 부분 결과 반환
자체 DB의 정보도 오래되거나 잘못될 수 있으므로 출처와 확인 시점을 함께 본다. 검색 첫 번째 결과나 이름 일치만으로 확정하지 않는다. 주소가 없는 장소도 검색 대상에 포함한다.
카카오 로컬 API는 키워드 장소 검색과 주소 좌표 변환을 제공한다. 장소 식별에는 키워드 검색 결과의 장소명·주소·ID 등을 활용하고, 주소 좌표 변환 결과만으로 해당 가게라고 단정하지 않는다. 지도 제공 주소는 캡션의 address_raw를 덮어쓰지 않는다.
5. 데이터 구성 제안
논리 데이터
주요 내용
추출 작업
사용자, 원본·정규화 URL, 게시물 ID, 단계·상태, 오류, 처리 시각
게시물 추출 결과
캡션 또는 필요한 근거, 출처, 완전성, 수집 시각, 추출기 버전
자체 장소
자체 place_id, 이름·별칭·지점, 주소·좌표, 출처·확인 시점
외부 장소 연결
제공처와 외부 장소 ID, 자체 place_id와 연결, 확인 상태
게시물–장소 연결
추출 후보, 원문 근거, 연결 장소, 확정 여부
사용자 저장
사용자와 장소의 연결, 사용자별 메모·수정
위 목록은 논리적 구분이며 모두 별도 테이블이어야 한다는 뜻은 아니다. 동일 장소를 여러 게시물이 소개하면 장소는 공유하고 출처 연결만 추가한다. 사용자 한 명의 수정은 공용 장소 정보를 즉시 덮어쓰지 않는다.
기존 DB가 없다면 단일 서버 시제품은 SQLite로 시작할 수 있다. 다중 인스턴스·동시 쓰기 요구가 확인되면 서버형 관계형 DB를 선택한다. 규모가 정해지기 전에 검색 엔진·벡터 DB·여러 서비스 분리는 도입하지 않는다.
미확정 후보 예시:
{  "name_raw": "덕진공원",  "address_raw": null,  "region_raw": "전주",  "evidence": "📍전주 덕진공원 일원",  "place_id": null,  "map_match": null,  "status": "needs_confirmation"}
작업 실패와 장소 없음은 구분한다. 예를 들어 fetch_failed, caption_not_found, caption_mismatch, no_places, needs_confirmation, completed는 서로 다른 결과다. HTTP 200만으로 작업을 성공 처리하지 않는다.
6. 주의사항과 현재 코드의 한계
정확성
현재 CSS 클래스 선택자는 변경에 취약하며 줄바꿈 &lt;br&gt;도 전제로 한다. 짧은 캡션·다른 레이아웃에서는 실패할 수 있다.
현재 JSON 검사는 페이지에서 찾은 캡션 중 일치하는 값을 검사한다. 운영용으로는 게시물 ID 결합 검사를 추가해야 한다.
현재 코드는 JSON 기준 캡션이 없을 때도 비교 결과를 false로 만든다. 운영용에서는 미확인 null과 불일치 false를 분리해야 한다.
규칙 파서는 번호 없는 복수 장소, 지번주소, 층·호수, 지점명 등을 일반적으로 처리하지 못한다.
덕진공원처럼 주소 없는 장소의 이름 정리에도 현재 표본에 특화된 규칙이 있다. 이를 범용 추출 정확도로 보고하지 않는다.
현재 evidence는 일부 줄을 조합한 문자열이다. 운영용에서는 원문 구간을 정확하게 보존하는 편이 검증에 유리하다.
게시물 수정·삭제와 장소 이전·폐업을 고려해 확인 시각을 기록하고, 결과 재사용 기간과 갱신 정책을 정한다.
보안과 운영
URL은 파서로 검사하고 HTTPS·허용 호스트·경로를 제한한다. 호스트가 문자열에 포함된다는 이유만으로 허용하지 않는다.
리디렉션 및 브라우저 하위 요청을 통한 내부망 접근을 막아 SSRF를 방지한다. 작업 환경의 네트워크 접근 범위도 제한한다.
API 키와 인증정보를 앱·소스·로그에 넣지 않는다. 사용자 간 작업 조회·저장 권한을 분리한다.
개인 브라우저 쿠키를 서버에 복사하지 않는다. 로그인·CAPTCHA·접근 제한을 만나면 명시적 실패로 처리하고 무한 재시도하지 않는다.
전체 작업 제한 시간과 동시 실행 제한이 필요하다. 현재 페이지 이동·요소 대기 시간 제한만으로 운영 전체가 보호되는 것은 아니다.
검증 코드는 fetch/XHR 응답 본문을 메모리에 모아 진단한다. 서비스에서는 이 수집을 상시 켜두지 말고 필요한 최소 로그만 남긴다.
동일 게시물의 중복 실행·중복 저장을 제어하고 실패 단계와 추출기 버전을 기록한다.
캡션·외부 API 응답의 저장 범위와 보관 기간을 정한다. 외부 LLM을 사용하면 전달 데이터·비용·보관 조건을 별도로 검토한다.
기술적 접근 성공은 플랫폼의 수집·이용 허용 여부 검토를 대체하지 않는다. 출시 전 Instagram 접근 방식과 지도 제공 데이터 저장·표시 조건을 확인한다. 이 문서는 법률·약관 적합성 판정이 아니다.
증거와 재실행
이번 문서는 기존 실행 산출물을 대조해 작성했다. 작성 시점에 게시물 네트워크 검증을 다시 수행한 것은 아니다.
verify_instagram.cjs는 운영 API가 아닌 두 URL 고정 검증 스크립트다.
재실행하면 instagram_results.json과 캡션 TXT를 덮어쓴다. 비교용 기존 결과는 먼저 별도 보관한다.
일반 HTTP 검사 결과는 별도 절차로 추가했다. 스크립트만 재실행하면 해당 비교 항목이 복구되지 않는다.
7. 다음 구현·검증 순서
1. 실제 배포 예정 서버에서 같은 두 URL을 재검증한다. 로컬 결과를 서버 성공으로 대체하지 않는다.
2. 기존 추출 코드를 입력 URL을 받는 백엔드 작업으로 바꾸고 인증·격리·시간 제한·실패 상태를 추가한다.
3. 앱에서 작업 상태, 원문 근거, 장소 후보를 보여준다.
4. 자체 DB 검색과 외부 API 보완을 연결하고 모호한 결과는 사용자가 선택하게 한다.
5. 사용자 저장과 중복 연결 방지, 출처·확인 시점 기록을 구현한다.
6. 단일·복수 장소, 주소 없음, 짧은 캡션, 릴스, 이미지에만 주소가 있는 경우, 접근 실패를 포함한 별도 표본으로 평가한다.
완료 판단은 단계별로 한다. 캡션 확보율, 캡션 전체 일치 여부, 장소 누락·오연결, 지도 장소 연결 정확도, 처리 시간·실패율을 각각 기록한다. 아직 목표 수치나 실제 운영 성능을 정하거나 측정하지 않았다.
