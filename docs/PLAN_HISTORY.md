# STOG 과거 결정과 작업 이력

[PLAN.md](PLAN.md)에서 내용 변경 없이 옮긴 역사 기록이다. 현재 상태와 다음 작업은 PLAN이 소유한다. 과거 결정이나 증거를 찾을 때만 읽고, 새 작업 기록은 `## 작업 이력` 표의 맨 위에 추가한다.

### 역사적 foundation/auth 결정과 당시 blocker

아래 항목의 Kakao Android SDK, base URL 미설정과 QA process 종료는 당시 기록이며 현재 Android 상태를 뜻하지 않는다. 현재 상태는 위의 최신 결정과 native TASK를 따른다.

- `CONFIRMED`: Android source는 Java/XML이며 개발 기본값은 `minSdk 23`, `targetSdk 36`, `compileSdk 37`, JDK 17.0.11, AGP 9.3.2, Gradle 9.5.0이다. 이 값은 Kakao SDK 호환성 검증을 대신하지 않는다.
- `CONFIRMED`: 제품은 추가 비용 0원이며 유료 fallback을 허용하지 않는다. 실제 Kakao 계정의 무료 이용 자격, quota, billing 상태, 한도 초과 차단 또는 중단 방법을 확인하기 전에는 연결하지 않는다.
- `CONFIRMED`: backend 보호 동작은 요청의 `user_id`가 아니라 검증된 내부 `principal_user_id`만 사용한다. 현재 positive test principal은 test-only다.
- `CONFIRMED`: Kakao Login은 첫 provider이며, 최초 자동 provisioning, 동일 검증 identity 재로그인 계정 해석, email 자동 merge/link 금지 정책이 기록됐다.
- `CONFIRMED`: 첫 성공 검증 Kakao login은 내부 STOG 계정 하나를 자동 생성하고, 같은 검증된 Kakao identity의 이후 login은 같은 내부 계정으로 해석한다. email을 기준으로 자동 merge/link하지 않는다.
- `CONFIRMED`: backend 개발·시험 원본은 사용자의 local PC에 유지한다. 사용자는 direct public access 준비를 요청했다. host NIC에 public-range IPv4가 직접 할당된 관찰이 있으므로 router forwarding은 필수이거나 가능하다고 입증되지 않았고, routed private LAN으로 확인되는 경우에만 조건부 경로다. 실제 public start, interface/port, DNS/TLS route, proxy, deployment와 callback 공개는 아직 승인하지 않았다. server/API 설정은 중앙에서 관리하고 secret은 ignored local developer config에만 둔다. Cloudflare Tunnel은 현재 실행에서 선택되지 않았다.
- `IMPLEMENTED / local VERIFIED`: `backend/src/main/resources/application.properties`는 loopback `server.address=127.0.0.1`과 명시 `server.port=8080`을 중앙 기본값으로 둔다. `LOCAL-BACKEND-001`의 isolated PostgreSQL, DPAPI-backed startup, Flyway V1과 local protected `401`은 실제 검증했고 QA app process는 종료했다. Android source에는 fail-closed `stog.server.baseUrl` consumer가 있으며 실제 값은 미설정이다. 승인된 LAN-bound TLS reverse proxy 또는 명시적 application LAN binding과 모든 external runtime은 `NOT_RUN`이다.
- `IMPLEMENTED / local VERIFIED`: backend는 `(KAKAO, canonical service user id)` mapping, app-bound token-info/user-info 검증, atomic duplicate identity 처리, hash-only opaque access/refresh, 15분/30일/90일 DEVELOPMENT 수명, rotation/replay revoke/current-session logout과 Bearer principal filter를 사용한다. Explicit restricted-owner mode는 configured existing internal owner만 exchange/refresh/access를 허용하고 missing/malformed config를 startup fail-closed하며 disabled baseline을 바꾸지 않는다.
- `IMPLEMENTED / local VERIFIED`: Android는 ignored local/environment 설정, `v2-user:2.25.0`, `kakao{NATIVE_APP_KEY}://oauth`, release HTTPS/debug literal-loopback 제한, memory-only access와 Keystore AES/GCM refresh, refresh/logout lifecycle을 사용한다. fixture token/HTTP와 missing-config device를 검증했고, 실제 Kakao local loopback login/logout/relogin도 bounded runtime으로 확인했다.
- `CONFIRMED`: 본인이 현재 개발·테스트 Kakao 앱과 STOG backend의 승인 및 데이터 운영을 단독으로 책임진다. 이는 `TripMember` 역할과 별개다. 법적 소유권 확인, console 권한 감사, 비용 확인, 삭제·보관 승인과 public exposure 권한을 확인하거나 부여한 기록은 아니다.
- `BLOCKED / NOT_APPROVED`: restricted-owner backend gate(item 1)는 local 검증됐지만 item 2인 Caddy/Posh-ACME download/install과 public start/network/TLS는 승인되지 않았다. Public runtime은 inbound 권한과 direct-public bind 또는 승인된 routed mapping 중 하나가 확인된 뒤 별도 승인까지 필요하다. 그 전에는 loopback-only를 유지한다.
- `LOCAL FIXTURE + REAL BACKEND VERIFIED`: protected current TripItem GET은 synthetic provider identity와 generated isolated rows를 사용한 Android emulator -> existing local backend -> PostgreSQL 경계에서 확인됐다.
- `NOT_RUN`: real Kakao와 protected TripItem을 결합한 production E2E, configured production Android login, public-network E2E, provider consent/account 화면 관찰.

## 역사적 인증 workstream 순차 체크리스트

아래는 Kakao 선택을 구현 승인으로 오해하지 않도록 나눈 bounded work session이다. 각 session의 작은 항목은 한 번에 처리하고, 큰 session 끝에만 전체 검증 gate를 둔다. behavior 변경이 있으면 구현 전에 최소 failing-first 증거를 남긴다. 문서 작업인 현재 session에는 runtime 검증을 요구하지 않는다.

### 세션 0, 선택 기록과 착수 조건

- [x] Kakao를 첫 provider로 기록하고 다른 provider의 병렬 작업을 열지 않는다.
- [x] 사용자가 정할 항목 중 자동 provisioning과 기존 계정 linking·병합 정책을 확인한다: 첫 성공 검증 login은 내부 계정 하나를 만들고, 같은 검증 identity는 그 계정으로 해석하며, email로 자동 merge/link하지 않는다.
- [ ] 남은 사용자 결정: 무료 한도 초과 시 즉시 중단 여부, identity metadata 보관 기간, duplicate identity 처리. beta 삭제·복구와 첫 외부 tester 범위는 timeout에 따른 `DELEGATED BEST-JUDGMENT DEFAULT`로 owner-assisted deletion preparation과 owner-only restricted external test preparation을 채택했다. 이는 구현이나 명시적 개인 선택이 아니다.
- [ ] 엔지니어가 정할 수 있는 세부사항은 답을 기다리지 않고 제안한다: 공식 문서 기반의 최소 흐름, fail-closed 오류, 비밀값 보관 경로, 테스트 경계.
- 선행조건: 사용자 선택 기록. 수용 기준: Kakao만 `CONFIRMED / selected first provider`이고 provisioning 정책만 확정되며 billing, session, 구현 승인은 계속 별도 상태다.
- 종료 검증 gate: 문서 QA-by-read. Kakao 선택, 미결정 목록, 현재 슬롯이 서로 일치해야 한다. 당시 planning runtime은 `NOT_RUN`; 후속 bounded local runtime은 별도 artifact에 기록됐다.

### 세션 1, 실제 계정과 기술 경로 확인

- [x] direct public reachability의 조건부 network path와 안전한 local backend 설정을 [QUALITY_OPERATIONS](QUALITY_OPERATIONS.md#backend-local-설정과-시작-절차)에 문서화하고 검증했다. Public-address NIC는 승인된 interface bind/firewall, routed private LAN은 그 경우에만 router mapping이 필요하다. 실제 public start와 구체 network/TLS/LAN 경계는 미승인이며 현재 runtime 성공 기준은 protected endpoint의 외부 `401`뿐이다. [TASK](tasks/DIRECT-PUBLIC-ACCESS-001.md); [Cloudflare 준비](tasks/CLOUDFLARE-TUNNEL-001.md)는 deferred다.
- [ ] Kakao Developers 앱과 Android 플랫폼·redirect 설정의 console 권한을 감사한다. 본인의 운영 책임 결정은 이미 기록됐지만 법적 소유권 확인으로 간주하지 않는다. credential 값은 받거나 문서에 기록하지 않는다.
- [ ] 실제 계정의 무료 이용 자격, quota, billing 상태, 지출 차단 또는 한도 초과 중단을 확인한다. 확인되지 않으면 연결하지 않는다.
- [ ] Java/XML 앱과 `minSdk 23`에서 사용할 지원 SDK·버전과 공식 통합 경로를 확인하고, 불일치하면 승인 전에 대체 구현 경계를 제시한다.
- [ ] redirect URI, custom scheme 또는 app link, PKCE 사용 여부와 callback 책임을 결정한다. 외부 token을 내부 principal로 직접 신뢰하지 않는다.
- 선행조건: 세션 0의 사용자 운영 조건. 수용 기준: 계정·비용·호환성·redirect 확인 결과와 미확인 항목이 기록되고, 승인 없는 서비스 연결은 없다.
- 종료 검증 gate: 문서와 공식 출처 대조, 계정 화면 확인 기록 QA. runtime `NOT_RUN` 또는 실제 확인 시 그 범위만 기록한다.

### 세션 2, identity mapping과 인증 상태 계약

- [ ] 검증된 Kakao identity의 stable key와 내부 User의 매핑을 정한다. email을 단독 key로 가정하지 않는다.
- [x] 최초 login provisioning과 기존 계정 linking·병합의 기본 정책을 기록한다: 첫 성공 검증 login은 내부 계정 하나를 자동 생성하고, 같은 검증 identity는 같은 계정으로 해석하며, email로 자동 merge/link하지 않는다.
- [ ] duplicate identity, unlink, 삭제, 복구, display metadata 최소 필드와 보관 기간을 정한다.

- 종료 검증 gate: API, BACKEND, DATABASE 경계와 계약 QA-by-read. 구현 전 최소 failing-first 시나리오 목록을 확정한다. runtime `NOT_RUN`.
